# 计划

本文档在 [v0](./v0.md) 的基础上，给出第一版可实现的整体架构，并明确说明这套系统应如何使用 `stdexec` 的 `scheduler / sender / receiver`。

## plan_v1

状态：首版（冻结 `stdexec` 语义和整体模块边界）

### 1. 本版目标

`v0` 已经冻结了长期约束：

- 搜索侧的基本执行单元是 `playout coroutine`
- 搜索协程只有一个 yield 点
- 搜索侧的继续/停止决策必须下沉到 playout 边界
- GPU infer 完成后必须先重估目标，再唤醒等待中的搜索协程

`v1` 的目标是继续回答三件事：

1. 这套系统里，`scheduler / sender / receiver` 分别由谁承担什么职责。
2. 顶层模块应如何拆分，才能既符合 `stdexec` 习惯，也符合 `v0` 的单-yield 约束。
3. 从当前代码迁移时，哪些现有对象可以保留语义，哪些必须改名或降级成实现细节。

### 2. 从 v0 继承的硬约束

本版不重新讨论以下问题，它们已经是既定约束：

- 性能优先级高于抽象纯洁性。
- TensorRT-only fast path 允许存在。
- 搜索侧不能退化成高频中心轮询器。
- 搜索协程不能出现第二个真实 yield 点。
- GPU 侧必须拥有“先更新估计、再计算目标、后唤醒搜索协程”的明确时序。
- request 需求模型由 GPU 时间估计、单次 playout 平均 CPU 时间、单次 playout 成功概率共同决定。

### 3. `stdexec` 语义基线

#### 3.1 `scheduler` 的定位

在 `stdexec` 里，`scheduler` 是轻量句柄，不是状态容器。它只是某个执行上下文的调度入口。

因此本项目里：

- `SearchWorkerScheduler` 是“把搜索协程安排到某个 CPU 搜索 worker lane 上运行”的句柄。
- 它不是 `SearchThread`。
- 它也不是 `PlayoutContext`。
- 它更不是“当前搜索 worker 的全部状态对象”。

但搜索热路径不应建立在匿名通用线程池之上。

本版修正为：

- 生产方案里的搜索执行上下文应是 `SearchWorkerPool`
- `SearchWorkerPool` 的大小直接由 `numSearchThreads` 指定
- 它包含 `numSearchThreads` 个长期存在的 worker
- 每个 worker 暴露一个独立的 `SearchWorkerScheduler` handle

因此，搜索侧真正暴露给 `stdexec` 的不是“一个全局搜索 scheduler”，而是“一组固定 worker scheduler”。

`exec::static_thread_pool` 仍然可以用于：

- smoke test
- 小规模原型
- 非搜索热路径的辅助执行上下文

但不应成为最终搜索热路径的执行模型，因为：

- 无法自然表达“worker 0..N-1 各有一个固定 lane”
- 无法直接保证启动时对每个 worker 恰好播种一次
- 容易引入额外的排队、迁移和 cache 亲和性损失

#### 3.2 `sender` 的定位

`sender` 是模块之间表达异步边界的公共语言。

本项目里，真正应该以 sender 形式暴露的边界只有两类：

- 顶层 runtime 生命周期边界
  - 例如 `on_drained()`
  - 例如 `scope.on_empty()`
- NN 提交与完成边界
  - 例如 `NNRequestLayer::submit(...) -> sender<NNEvalResult>`

搜索树推进、共享区统计更新、GPU 时间模型更新，本质上都是同步状态机步骤，不应伪装成 sender。

#### 3.3 `receiver` / `operation_state` 的定位

`receiver` 和 `operation_state` 在这套系统里必须严格留在 sender 实现内部。

也就是说：

- `SearchTreeCore`
- `PlayoutRuntime`
- `SearchSharedState`
- `DemandModel`

这些模块都不应该把 receiver/opstate 暴露成公共抽象。

它们只会出现在：

- `NNRequestLayer::submit()` 的 custom sender 实现内部
- `TensorRTRuntime::submit()` 的 custom sender 实现内部
- `async_scope`、`starts_on`、`sync_wait` 等 `stdexec/exec` 算法内部

#### 3.4 `exec::task` 的定位

搜索协程使用 `exec::task<void>`。

原因不是“它是现成 runtime”，而是：

- 它可以直接 `co_await` sender
- 它自带 stop token 语义
- 它默认是 scheduler-sticky

这对本项目特别关键：

- `run_one_playout()` 在某个 `SearchWorkerScheduler` 上启动
- 它 `co_await` `NNRequestLayer::submit()` 时会挂起
- 等 NN sender 完成后，协程恢复时仍然回到原搜索 scheduler 继续更新搜索树

因此：

- 搜索协程本身不需要保存 continuation handle 到 `NNRequest`
- `NNRequest` 也不该携带 callback token
- “恢复到搜索侧继续跑”由 `exec::task` 的 sticky 语义负责

如果未来确实需要显式迁移协程到别的搜索 shard，使用：

- `exec::reschedule_coroutine_on(other_sched)`

但这不是第一阶段的主路径。

#### 3.5 公用 Gamma 估计器

CPU 和 GPU 侧的近期时间估计都可以遵循同一套 gamma 衰减更新公式。

因此本版新增一个跨模块公用的小组件：

```cpp
class GammaEstimate {
 public:
  explicit GammaEstimate(double gamma, double initialValue);

  void observe(double sample);
  double value() const;
};
```

它只负责：

- 保存当前估计值
- 以 `estimate = gamma * estimate + (1 - gamma) * sample` 更新

它不负责业务语义。

也就是说：

- `SearchSharedState` 用它维护 `playoutCpuMs` 和 `requestSuccessProb`
- `TensorRTRuntime::TimingModel` 用它维护 `inferMs` 或 `batchServiceMs`

复用的是数学工具，而不是把 CPU 和 GPU 时间模型硬揉成一个对象。

### 4. 整体模块划分

本版确定以下五层结构：

1. `SearchTreeCore`
2. `SearchSharedState`
3. `PlayoutRuntime`
4. `NNRequestLayer`
5. `TensorRTRuntime`

其中：

- `SearchTreeCore` 负责树语义
- `SearchSharedState` 负责共享统计区和 gate
- `PlayoutRuntime` 负责搜索协程生命周期
- `NNRequestLayer` 负责把“搜索需要一次 NN”变成 sender
- `TensorRTRuntime` 负责真正的 TensorRT request/batch/stream 状态机

### 5. 每层的职责与公共边界

| 模块 | 主要职责 | 公共边界 | 是否使用 `scheduler` | 是否使用 `sender` | 是否直接实现 `receiver` |
| --- | --- | --- | --- | --- | --- |
| `SearchTreeCore` | 单次 playout CPU 相位、路径推进、virtual loss、eval 回填 | 同步值类型 API | 否 | 否 | 否 |
| `SearchSharedState` | 全局 NNEval 计数、当前窗口绝对目标水位线、启停 gate、gamma 衰减统计量、全局 stop | 原子/同步 API | 否 | 否 | 否 |
| `PlayoutRuntime` | `exec::task` 生命周期、初始播种、drain、stop | `start()/stop()/on_drained()` | 是 | 是 | 否 |
| `NNRequestLayer` | 请求物化、cache、停止前 admission 判断、对搜索侧暴露 submit sender | `submit() -> sender<NNEvalResult>` | 否 | 是 | 内部是 |
| `TensorRTRuntime` | TensorRT request/batch/stream 状态机、GPU completion 时序 | backend-private sender API | 内部可有 | 是 | 内部是 |

### 6. 共享区设计

`v0` 要求搜索侧存在一个共享区域。本版将它具体化为一个普通状态对象，而不是 runtime 或 scheduler。

```cpp
struct SearchSharedState {
  stdexec::inplace_stop_source stopSource;

  // 当前需求窗口的版本号。每次 GPU completion 发布新窗口后递增。
  std::atomic<uint64_t> epoch;

  // 全局累计：已经逻辑提交的 NN request 数量。
  std::atomic<uint64_t> issuedNNEvalCount;

  // 全局累计：已经 publish completion 的 NN request 数量。
  std::atomic<uint64_t> completedNNEvalCount;

  // 当前窗口发布的绝对目标水位线。只有当 issued < targetIssued 时，
  // 搜索侧才应继续生成新的 NN request。
  std::atomic<uint64_t> targetIssuedNNEvalCount;

  // generation gate 的快速提示位，不是唯一的正确性来源。
  std::atomic<bool> generationOpen;

  // 当前活跃搜索协程数量，仅用于播种和观测，不参与热路径复杂决策。
  std::atomic<int> liveCoroutines;

  // gamma 衰减均值。
  GammaEstimate playoutCpuEmaMs;
  GammaEstimate requestSuccessEma;
};
```

#### 6.1 共享区上的 `O(1)` 更新

单次 playout 结束时只允许做常数时间更新：

- `playoutCpuEmaMs = gamma * old + (1 - gamma) * sample`
- `requestSuccessEma = gamma * old + (1 - gamma) * produced_request`
- 若产出 request，则 `issuedNNEvalCount += 1`
- GPU completion publish 时，`completedNNEvalCount += batchSize`

`GammaEstimate` 内部可以直接使用 `atomic<double>` + CAS loop，或者用缩放后的整数定点数；`v1` 先不锁死实现。

#### 6.2 gate 语义

本版修正为：

- 正确性的权威状态不是局部 `outstanding target`
- 而是全局累计计数上的关系：
  - `issuedNNEvalCount`
  - `completedNNEvalCount`
  - `targetIssuedNNEvalCount`
- 搜索侧是否还能继续生成新的 request，权威判断是：
  - `issuedNNEvalCount < targetIssuedNNEvalCount`

其中：

- `targetIssuedNNEvalCount` 是当前窗口发布的绝对目标水位线
- 它通常由 GPU completion 按
  - `completedNNEvalCount + desiredOutstandingNN`
  计算得到
- `generationOpen` 仍可保留，但只能是快速提示位，不得替代计数比较本身
- `epoch` 用于标记 GPU 已发布了哪一版窗口快照

这样做的原因是：

- 搜索协程在 playout 内不可打断
- 达到目标后允许存在少量额外 NN 提交
- 这些额外提交必须被精确计入全局累计状态，而不是靠局部 outstanding target 猜测

### 7. `scheduler / sender / receiver` 在系统里的具体用法

#### 7.1 `SearchWorkerPool` / `SearchWorkerScheduler`

`SearchWorkerScheduler` 只干一件事：

- 让搜索协程的 CPU 相位在搜索执行上下文上运行

但这里的“执行上下文”不是匿名线程池，而是固定 worker lane。

本版确定：

- `numSearchThreads` 直接决定 `SearchWorkerPool` 的大小
- runtime 启动时必须枚举 `workerIdx = 0..numSearchThreads-1`
- 对每个 worker 恰好启动一个长期存在的 worker driver

顶层注入方式因此改为：

```cpp
for (int i = 0; i < numSearchThreads; i++) {
  scope.spawn(stdexec::starts_on(workerSched[i], run_search_worker(runtime, i)));
}
```

这里：

- `run_search_worker(...)` 是长期存在的 `exec::task<void>`
- `starts_on` 负责把它放到搜索 scheduler 上启动
- `async_scope` 负责追踪生命周期

这样就能保证：

- 启动时恰好播种 `numSearchThreads` 个 worker
- 不重不漏，因为 worker 是按 index 显式枚举的
- 之后热路径不再依赖匿名线程池决定“这次 playout 落到哪个线程”

不允许用法：

- 不允许把 `scheduler` 当成 `SearchThread`
- 不允许用 `schedule()` / `yield()` 人工制造第二个 yield 点
- 不允许再引入中心 `tick()` 循环去决定每次是否投放 playout
- 不允许把匿名 work-stealing / 通用线程池作为搜索热路径的最终执行模型

#### 7.2 为什么这比通用线程池更合适

根据 `v0` 的目标，搜索调度大部分时间应是静态的：

- 一个 worker 上的一次 playout 结束后
- 若没有挂起等 NN
- 通常应由同一线程原地开始下一次 playout

因此热路径理想形态是：

- 固定 worker
- 固定 lane
- 强亲和性
- 最少的跨线程迁移

通用线程池最大的问题不在“不能运行”，而在它默认提供的是更通用的任务分发语义：

- 额外排队
- 可能的线程迁移
- 更弱的 cache 亲和性
- 更难精确表达“每个搜索线程上各自维护一条本地热路径”

所以本项目里：

- `stdexec::scheduler` 抽象照样用
- 但底层 execution context 需要是搜索专用的固定 worker 池，而不是通用池

#### 7.3 `NNRequestLayer::submit()`

`NNRequestLayer` 向搜索侧暴露的主接口固定为：

```cpp
auto submit(NNRequest req, SearchSharedState& shared) -> stdexec::sender auto;
```

语义是：

- 若 stop 已请求，且 request 还未进入 backend，可 `set_stopped()`
- 若 request 成功进入 backend，则 completion 最终以：
  - `set_value(NNEvalResult)`
  - `set_error(std::exception_ptr)`
  的形式返回

搜索侧使用方式固定为：

```cpp
NNEvalResult result = co_await requestLayer.submit(std::move(req), shared);
```

#### 7.4 `receiver` 的具体落点

搜索侧不手写 receiver。

真正要手写 receiver/opstate 的地方在 `NNRequestLayer::submit()` 和 `TensorRTRuntime::submit()`：

- operation state 持有：
  - downstream receiver
  - request record / slot handle
  - admission 状态
  - completion 状态
- runtime 完成请求时，按 `stdexec` 约定调用：
  - `set_value`
  - `set_error`
  - `set_stopped`

搜索协程 `co_await` sender 时，`exec::task` 会自动生成适配它的 receiver。

### 8. 单-yield 搜索协程协议

本版把搜索执行拆成两层：

- 顶层是长期存在的 worker driver
- 逻辑上的基本工作单元仍然是 playout coroutine

顶层 worker driver 先固定为：

```cpp
auto run_search_worker(PlayoutRuntime& runtime, int workerIdx) -> exec::task<void>;
```

逻辑 playout 单元固定为：

```cpp
auto run_one_playout(PlayoutRuntime& runtime, PlayoutContext ctx) -> exec::task<void>;
```

其中 `PlayoutContext` 是协程私有状态，不是线程状态。第一阶段可以从现有 `SearchThread` 演化而来，但语义必须改成：

- coroutine-local
- move-only
- 与 OS thread 脱钩

这里特别强调：

- `run_one_playout(...)` 是逻辑工作单元
- 但不是“每次都从全局 runtime 重新 spawn 的匿名 task”
- 常见热路径应由 `run_search_worker(...)` 在同一 worker 上直接继续下一次 playout
- 只有在某个 playout 因 `co_await submit(...)` 挂起后，这个 worker 才去接着跑别的本地 playout

#### 8.1 worker driver 主循环

```text
worker loop:
  1. 若本地有可恢复的 suspended playout，则优先恢复
  2. 否则若共享区允许继续生成，则原地启动下一次新的 playout
  3. 否则进入 parked 状态，等待：
     - GPU completion 打开新一轮 generation
     - 或全局 stop
```

这意味着：

- worker 是长期存在的
- 线程也是长期存在的
- “一次 playout 结束后原地开始下一次 playout”是默认快路
- scheduler 入队主要发生在：
  - 启动时播种 worker
  - GPU completion 把某个挂起 playout 恢复回 home worker
  - 少数需要显式迁移的场景

#### 8.2 单次 playout 协议

```text
loop:
  1. 同步执行一次 CPU 相位 playout
  2. 更新共享区统计量
  3. 若未产出 request:
     - 检查 issuedNNEvalCount < targetIssuedNNEvalCount
     - true -> 继续 loop
     - false/stop -> return
  4. 若产出 request:
     - myIssued = ++issuedNNEvalCount
     - 读取当前 targetIssuedNNEvalCount
     - 若 myIssued >= targetIssuedNNEvalCount:
         generationOpen = false  // hint only
       否则:
         由当前 worker driver 继续保证本地热度
     - co_await submit(...)
     - apply_eval(...)
     - 回到 loop
```

这里允许出现少量：

- `issuedNNEvalCount > targetIssuedNNEvalCount`

因为其它 worker 上已经在本地 CPU 相位中运行的 playout 可能也会在稍后抵达边界并产出 request。  
这不是错误；后续窗口会基于最新全局累计计数自然吸收它。

整个热路径里唯一允许挂起的地方是：

- `co_await submit(...)`

#### 8.3 为什么这样满足 `v0`

- 未产出 request 的 playout：没有任何 suspension
- 产出 request 的 playout：只在等 GPU 结果时挂起
- GPU 完成前，当前协程的树路径局部状态保存在 coroutine frame / `PlayoutContext`
- GPU 完成后，协程回到原 home worker scheduler 上继续 `apply_eval`
- 同一 worker 上下一次 playout 的启动通常是原地发生，而不是重新走一次全局任务分发

### 9. GPU completion 时序

这是本版最关键的时序约束。

当 `TensorRTRuntime` 检测到一个 infer batch 完成时，顺序必须严格如下：

1. 更新 GPU 侧近期时间估计
2. 结合：
   - 新的 GPU 时间估计
   - `playoutCpuEmaMs`
   - `requestSuccessEma`
   计算下一窗口期望维持的 `desiredOutstandingNN`
3. 递增 `completedNNEvalCount`
4. 计算并覆盖写入：
   - `targetIssuedNNEvalCount = completedNNEvalCount + desiredOutstandingNN`
   - `generationOpen = (issuedNNEvalCount < targetIssuedNNEvalCount)`
5. 发布新的 `epoch`
6. 只有在这之后，才对等待中的 request sender 调用 completion

也就是说，等待中的搜索协程被恢复时，看到的共享区已经是“新窗口”状态。

这正对应 `v0` 的要求：

- 先更新估计
- 再计算目标
- 再唤醒搜索协程

### 10. 顶层对象关系

```text
Search
  -> SearchSession
       -> SearchSharedState
       -> PlayoutRuntime
       -> SearchTreeCore
       -> NNRequestLayer
       -> TensorRTRuntime
```

其中：

- `SearchSession` 是拥有者和装配层，不是高频调度循环
- 高频决策发生在：
  - playout 边界
  - GPU completion 边界
- 高频热路径默认局限在 worker-local lane 内部

### 11. 从当前代码迁移的映射

#### 11.1 `SearchThread`

现有 `SearchThread` 里真正有价值的是：

- board/history/graphPath
- rand
- `NNResultBuf`
- 各类 scratch buffer

这些都应保留，但语义改成：

- `PlayoutContext`
- coroutine-local
- 与固定搜索线程解绑

因此：

- `SearchThread` 不是 scheduler
- `SearchThread` 也不该继续代表“长期绑定某个 OS 线程的搜索 worker”

#### 11.2 `NNEvaluator::evaluate`

现有同步阻塞入口仍可作为第一阶段底层实现素材，但对搜索侧公共边界要升级为：

- `NNRequest`
- `NNEvalResult`
- `submit() -> sender`

#### 11.3 当前线程池搜索循环

现有 “固定线程 + while loop + 阻塞 evaluate” 的结构，在新方案中拆成：

- `SearchTreeCore` 的同步 CPU 相位
- `PlayoutRuntime` 的 `exec::task` 生命周期
- `NNRequestLayer/TensorRTRuntime` 的 sender completion

### 12. 本版明确排除的方案

以下方案从 `v1` 起明确视为错误方向：

- 中心 `session.tick()` 高频轮询驱动搜索
- permit queue 驱动的 per-playout task 模型
- 匿名通用线程池直接承担搜索热路径
- 把 `receiver` / `operation_state` 设计成系统公共抽象
- 把 `SearchThread` 直接等价为 `scheduler`
- 在搜索协程热路径上加入第二个 yield 点

### 13. `v2` 需要回答的问题

下一版计划需要进一步细化以下内容：

- `SearchTreeCore` 应如何把“CPU 相位直到需要 NN”为止的同步逻辑拆成明确 API
- `SearchSharedState` 上哪些字段必须原子维护，哪些可以在较粗粒度锁下维护
