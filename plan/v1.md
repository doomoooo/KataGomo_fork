# v1 调度模型

本文档分两层：

1. 先给出不依赖任何具体异步运行时的抽象调度模型。
2. 再给出一个“如果从 0 开始就用 C++26 + stdexec 来写”的落地方案。

第二部分不是把旧实现包成 sender，而是反过来用 stdexec 的 execution context / sender / task 语义，直接组织一套原生设计。

另外，本文有意把“热路径控制流”和“异步边界”拆开：

- 热路径搜索推进尽量保持普通状态机，不把每一步都做成 sender。
- 真正跨线程、跨 execution context、需要等待通知的边界，才使用 stdexec 原语表达。

这样更接近零成本抽象，也更容易触发编译器优化。

## 0. 设计目标

本版冻结的不是某个 API 形状，而是以下几个更本质的约束：

1. 搜索侧自己参与 batch 构建，不能把 request 丢给独立数据面线程后完全抽身。
2. `pre_process()` 与 `post_process()` 都属于搜索侧，不回收进 GPU 控制面。
3. 搜索侧的新 root playout 与 NN 返回后的恢复 continuation 不是同优先级工作源。
4. 搜索侧与 GPU 侧的真实耦合点不是“提交一个 request”，而是“成功 claim 某个 open batch 的某一行”。
5. GPU timeline 的“预约”与“结算”是两个不同动作，不能合并。
6. batch handle 只能在最后一个消费者离开后复用。

这些约束在后面的 stdexec 方案里仍然保持不变。

## 1. 抽象模型

### 1.1 两个平面

系统拆成两个平面：

- 搜索平面：负责 playout 推进、leaf 选择、`pre_process()`、`post_process()`、回写树。
- 推理控制平面：负责 batch 生命周期、slot 选择、launch、timeline 预约与结算、结果发布。

关键点：

- 推理控制平面只拥有“batch 生命周期”的所有权。
- 搜索平面只拥有“row 内容”和“搜索 continuation”的所有权。
- 两边的边界是一条已经 claim 成功的 batch row。

### 1.2 工作单元

搜索平面的基本工作单元不是“线程绑定的协程”，而是“可迁移的 playout frame”。

一个 frame 至少包含：

- 当前搜索路径 / 显式栈
- 当前阶段
- 待恢复的 leaf 上下文
- 如果正在等 NN，则记录对应的 `BatchHandle + row`

frame 可以被任意搜索线程恢复执行；这是一条冻结约束。

### 1.3 搜索平面的两个工作源

搜索平面长期只看两个工作源：

1. 高优先级恢复队列：承接 NN 已完成、等待继续推进的 frame。
2. root 生成权限：当 credit/gate 允许时，发起新的 root playout。

调度原则固定为：

- 永远先消费高优先级恢复队列。
- 只有恢复队列为空且 root gate 打开时，才生成新的 root frame。

### 1.4 单调 credit 模型

搜索侧不把 NN“额度”理解为当前瞬时 outstanding 数，而理解为两个单调水位：

- `nn_issue_current`：已经累计发出的 NN 请求数。
- `nn_issue_target`：当前允许累计发出的 NN 请求目标数。

gate 规则：

- 当 `nn_issue_current >= nn_issue_target` 时，禁止生成新的 root frame。
- 这条规则只限制“新 root frame 的产生”。
- 它绝不能阻塞“已经在途 frame 的恢复”。

因此，高优先级恢复路径必须独立于 root gate。

### 1.5 BatchHandle 的抽象语义

`BatchHandle` 是 batch 句柄，不是 request 句柄。

它经历以下阶段：

1. `Open`
   - 允许搜索侧 claim row。
   - `claimed_rows` 表示下一可分配 row。
2. `Sealed`
   - batch 大小已经固定，不再允许 claim。
   - 推理控制平面等待所有已 claim row 的数据就绪。
3. `Inflight`
   - H2D / infer / D2H 正在进行。
4. `Published`
   - 结果已经写回 host buffer。
   - 对应 frame 已被重新投递到搜索恢复队列。
5. `Recyclable`
   - 所有消费者都完成 `post_process()`。
   - handle 才能返回空闲池重新作为 open batch 使用。

冻结约束：

- `Open -> Sealed` 是一次性状态跃迁。
- 谁完成这个跃迁，谁负责做 timeline reservation。
- reservation 只能做一次。

### 1.6 Row 发布语义

搜索侧 claim row 后：

1. 在搜索线程上执行 `pre_process()`。
2. 把 row 数据写入 handle 的 host staging 区。
3. 用正确的发布语义告诉推理控制平面“这一行已经可读”。

推理控制平面只有在确认 sealed batch 的所有已 claim row 都已 ready 后，才允许发起该 batch 的 H2D / infer。

这里冻结的是“发布-观察”关系，不冻结具体用 bitset、计数器还是别的实现。

### 1.7 结果恢复语义

当 D2H 完成后：

1. 推理控制平面更新 estimate。
2. 推理控制平面回写 timeline。
3. 推理控制平面更新 `nn_issue_target`。
4. 如果 root gate 从关闭转为可打开，则发通知给搜索平面。
5. 推理控制平面把本 batch 对应的 frame 投递回高优先级恢复队列。

注意：

- 推理控制平面不执行 `post_process()`。
- `post_process()` 在 frame 被搜索线程重新接手后执行。
- 这样才能保持“搜索线程自己消费 NN 结果”的 ownership。

### 1.8 Timeline 语义

GPU timeline 至少有四个动作：

- 选 slot
- seal 时预约 workload
- infer 完成后更新 estimate
- 用新 estimate 做 reconcile

并且顺序冻结为：

1. `update_gpu_estimate()`
2. `reconcile_gpu_timeline()`
3. `update_search_nn_target_num()`

搜索 credit 只能建立在 reconcile 后的估计之上。

### 1.9 v1 冻结的实现自由度

以下点允许实现自由：

- 推理控制面可以是“每 batch 一个 driver”，也可以是“每 slot 一个常驻 driver”。
- sealed batch 的 ready 判定可以是逐 row flag，也可以是 ready counter。
- 搜索 frame 可以由协程承载，也可以由显式状态机承载。

以下点不允许漂移：

- 搜索 continuation 必须高优先级。
- continuation 必须可被任意搜索线程恢复。
- `pre_process()` / `post_process()` 不能集中挪到 GPU 控制面。
- handle 必须等最后一个消费者离开后才能复用。
- timeline reservation / reconcile 不能混为一谈。

## 2. 从 0 开始的 stdexec 设计

这一节不讨论“怎么给旧代码套 sender”，而是直接给出一套原生 stdexec 架构。

核心策略是：

- 用 `exec::task<void>` 承载常驻 worker / driver 循环。
- 用 `exec::async_scope` 托管后台任务生命周期。
- 用 `exec::static_thread_pool` 承载搜索 worker。
- 用 `exec::single_thread_context` 承载串行的 slot driver。
- 热路径 playout 继续用显式状态机和 intrusive queue，不把 frame 本身做成 `any_sender`。

### 2.1 为什么这样映射

先说明几个 stdexec 事实，后面会反复用到：

1. `exec::task<T>` 本身就是 sender。
2. `ex::starts_on(sched, snd)` 是把一个 sender 的“启动点”放到 `sched` 上的标准方式。
3. `exec::async_scope` 适合托管长期后台任务；比 `exec::start_detached` 更适合核心子系统，因为它保留 stop 与 join 能力。
4. `exec::task` 默认是 sticky 的：
   - 它在哪个 scheduler 上启动，恢复后通常仍回到那个 scheduler。
   - 如果想让协程真正迁移到另一个 scheduler，需要显式 `exec::reschedule_coroutine_on(...)`。

这个 sticky 语义很重要，因此：

- 常驻的 `search_loop()` 和 `slot_driver()` 非常适合写成 `exec::task<void>`。
- 可迁移的 playout continuation 不适合直接写成“悬挂中的 `exec::task`”，因为它们需要被任意搜索线程恢复。
- 所以 playout frame 仍然应该是显式状态机对象，恢复时由哪个搜索 worker 拿到，就在哪个 worker 上同步推进。

这正好同时满足“逻辑等价”和“零成本倾向”。

## 3. stdexec 版运行时对象

```cpp
// 真实代码会拆头文件；这里为了讲清结构，先合在一起写。

#include <atomic>
#include <cstdint>
#include <memory>
#include <span>
#include <vector>

#include <stdexec/execution.hpp>
#include <exec/async_scope.hpp>
#include <exec/single_thread_context.hpp>
#include <exec/static_thread_pool.hpp>
#include <exec/task.hpp>

namespace ex = stdexec;

struct SearchFrame;
struct BatchHandle;

// 原生通知原语。
// 它不是为了包装旧 callback；它本身就是新设计里的基础同步单元。
// async_wait(pred) 返回一个 sender：
// - pred 已经成立则同步完成；
// - 否则把等待者挂进 intrusive waiter list，直到 notify_* 或 stop。
struct Notice {
  template <class Pred>
  auto async_wait(Pred pred) -> ex::sender auto;

  void notify_one() noexcept;
  void notify_all() noexcept;
};

// 搜索平面的共享 credit 状态。
struct SearchCredits {
  std::atomic<std::uint64_t> nn_issue_current{0};
  std::atomic<std::uint64_t> nn_issue_target{0};
};

// 高优先级恢复队列里放的不是 sender，也不是 std::function，
// 而是可迁移、可复用的 frame 指针。
// 这是热路径降本的关键之一。
struct SearchReadyQueue {
  void push(SearchFrame* frame) noexcept;
  auto try_pop() noexcept -> SearchFrame*;
  auto empty() const noexcept -> bool;
};

// 一个 GPU slot 一个串行 driver context。
// 这里选择 per-slot resident driver，而不是 per-batch driver，
// 因为从 0 开始设计时，这样更容易把“slot 生命周期”和“timeline 所有权”放在一起。
struct SlotRuntime {
  exec::single_thread_context ctrl_ctx;
  Notice                      notice;

  // 当前正在接收 claim 的 open batch。
  std::atomic<BatchHandle*> open_batch{nullptr};

  // 回收池，避免 steady-state 频繁分配。
  auto acquire_batch() -> BatchHandle*;
  void recycle_batch(BatchHandle* h) noexcept;
};

struct Runtime {
  exec::async_scope        scope;
  exec::static_thread_pool search_pool;
  std::vector<SlotRuntime> slots;

  SearchCredits    credits;
  SearchReadyQueue ready_q;
  Notice           search_notice;

  explicit Runtime(int num_search_threads, int num_slots)
      : search_pool(num_search_threads), slots(num_slots) {}
};
```

### 3.1 设计说明

- 搜索线程用 `exec::static_thread_pool`，因为本地 vendored stdexec 支持 `get_scheduler_on_thread(i)`，可以把常驻 worker 固定到具体线程上。
- slot driver 用 `exec::single_thread_context`，因为它天然就是“一个串行控制线程 + 一个 scheduler”，很适合承载“同一 slot 的 launch / reconcile / publish 必须串行化”这类职责。
- `Notice` 是原生 sender-based 等待点，不是旧式条件变量的适配层。
- `ready_q` 里不存 sender 图，而存 `SearchFrame*`，避免 type erasure、避免把热路径状态切碎成大量小 sender 对象。

## 4. 热路径状态对象

```cpp
enum class FramePhase : std::uint8_t {
  Descend,          // 正常搜索推进
  AwaitingNNResult, // 已经发出 NN，等 batch publish 后恢复
  Done,
};

struct PendingRow {
  BatchHandle* handle = nullptr;
  std::uint16_t row   = 0;
};

struct SearchFrame {
  FramePhase phase = FramePhase::Descend;

  // 显式搜索栈；省略具体节点字段。
  SearchPath path;

  // 若 phase == AwaitingNNResult，则这里记录恢复所需上下文。
  PendingRow pending;
  LeafData*  leaf = nullptr;

  // frame 完成后返回对象池，而不是 delete。
  FramePool* owner_pool = nullptr;
};

enum class BatchState : std::uint8_t {
  Open,       // 允许 claim
  Sealed,     // 大小固定，不再接受 claim
  Inflight,   // H2D / infer / D2H
  Published,  // 已把 frame 投递回 ready_q
};

struct BatchRow {
  // 谁在等这一行的结果。
  SearchFrame* frame = nullptr;
};

struct BatchHandle {
  std::atomic<BatchState> state{BatchState::Open};

  // 下一可 claim row。
  std::atomic<std::uint16_t> claimed_rows{0};

  // seal 后固定。
  std::atomic<std::uint16_t> sealed_rows{0};

  // 搜索侧完成 pre_process 后发布。
  std::atomic<std::uint16_t> ready_rows{0};

  // 搜索侧完成 post_process 后递减；为 0 才可回收。
  std::atomic<std::uint16_t> remaining_consumers{0};

  SlotId slot{};
  std::vector<BatchRow> rows;
  HostStagingBuffer     host_mem;
};
```

### 4.1 这里为什么不用协程表示 playout

因为 v1 要求 continuation 能被任意搜索线程恢复，而 `exec::task` 的默认 sticky scheduler 语义刚好与此相反。

因此，从 0 开始的 best practice 更像是：

- 常驻 worker/driver：`exec::task<void>`
- 可迁移 playout：显式 frame 状态机

这不是退回“手写 runtime”，而是把 stdexec 放在最合适的边界上使用。

## 5. 搜索 worker：常驻 task，frame 同步推进

```cpp
// 常驻搜索 worker。
// 这个 task 自身绑定在线程 i 上运行。
// 注意：它不是每次 playout 新建一个协程，而是一个长期存在的 worker loop。
auto search_loop(Runtime& rt, int worker_id) -> exec::task<void> {
  while (true) {
    // 原生等待点：等到“ready_q 非空”或“root gate 打开”。
    // async_wait 返回的是 sender，因此可以直接 co_await。
    co_await rt.search_notice.async_wait([&] {
      return !rt.ready_q.empty() || can_issue_new_root(rt.credits);
    });

    // 永远先恢复已经完成 NN 的 frame。
    if (SearchFrame* frame = rt.ready_q.try_pop()) {
      run_frame_until_boundary(rt, *frame);
      continue;
    }

    // ready_q 为空时，才允许生成新 root。
    if (can_issue_new_root(rt.credits)) {
      SearchFrame* frame = acquire_root_frame();
      run_frame_until_boundary(rt, *frame);
      continue;
    }

    // 可能是被别的 worker 抢空了 ready_q，也可能是 gate 在竞争中关闭了。
    // 直接回到 loop 顶部重新等。
  }
}
```

说明：

- 为了突出主调度结构，这里省略了 `set_stopped` 分支。
- 实际实现里，`Notice::async_wait(...)` 应该在 `async_scope` 的 stop token 被请求时完成为 `stopped`。
- `search_loop()` 收到这个停止完成后直接退出即可。

### 5.1 解释

- 这里把 `search_loop()` 写成 `exec::task<void>`，是因为它天生就是一个长期存在的异步主体。
- `co_await notice.async_wait(...)` 是合理的，因为“等待有新工作”确实是一个异步边界。
- `run_frame_until_boundary()` 则刻意不写成 sender，而写成普通同步状态机函数。
  原因是它是热路径，且中途只会在“需要 NN”这一处真正释放控制权。

## 6. frame 推进函数：同步状态机

```cpp
// 热路径推进：普通函数，不是 sender。
// 它会一直推进到以下两个边界之一：
// 1. frame 完成；
// 2. 需要 NN，于是把自己挂到某个 batch row 上，然后立即返回。
void run_frame_until_boundary(Runtime& rt, SearchFrame& frame) {
  while (true) {
    switch (frame.phase) {
      case FramePhase::AwaitingNNResult: {
        // 重要：post_process 仍在搜索线程上做，而不是在 slot driver 上做。
        auto* handle = frame.pending.handle;
        auto  row    = frame.pending.row;

        post_process(handle->host_mem.view(row), *frame.leaf);

        // 这是最后一个消费者则负责 recycle。
        if (handle->remaining_consumers.fetch_sub(1, std::memory_order_acq_rel) == 1) {
          recycle_batch_handle(rt, handle);
        }

        frame.pending = {};
        frame.phase   = FramePhase::Descend;
        break;
      }

      case FramePhase::Descend: {
        StepResult step = advance_one_search_step(frame.path);

        if (step.kind == StepKind::Done) {
          frame.phase = FramePhase::Done;
          break;
        }

        if (step.kind == StepKind::NeedNN) {
          issue_nn_and_yield(rt, frame, step.leaf);
          return;
        }

        // 否则继续在 while 内推进，不释放控制权。
        continue;
      }

      case FramePhase::Done: {
        release_frame(frame);
        return;
      }
    }
  }
}
```

### 6.1 这里体现了哪些 v1 约束

- continuation 不是“恢复原协程”，而是“恢复显式 frame”。
- frame 可以被任意 worker 拿到并继续。
- `post_process()` 保持在搜索平面。
- 不保留深层协程调用栈。

## 7. claim + pre_process：搜索侧提交 NN

```cpp
void issue_nn_and_yield(Runtime& rt, SearchFrame& frame, LeafData& leaf) {
  // 单调累计计数。
  std::uint64_t cur =
      rt.credits.nn_issue_current.fetch_add(1, std::memory_order_acq_rel) + 1;
  std::uint64_t tgt =
      rt.credits.nn_issue_target.load(std::memory_order_acquire);

  // 如果越过 target，仅关闭“新 root 生成”这条路；
  // 已在途 frame 的恢复不受影响。
  if (cur >= tgt) {
    // 这里不需要单独的 pause bool。
    // 直接把 gate 定义成 (current < target) 更干净。
  }

  ClaimResult claim = claim_open_row(rt, frame);

  // 搜索线程自己做预处理。
  pre_process(leaf, claim.handle->host_mem.mutable_view(claim.row));

  // frame 记录恢复点。
  frame.leaf         = &leaf;
  frame.pending      = PendingRow{claim.handle, claim.row};
  frame.phase        = FramePhase::AwaitingNNResult;

  // 这一行对应哪个 frame，由搜索侧写入。
  claim.handle->rows[claim.row].frame = &frame;

  // 用 release 语义发布 row 数据已可读。
  claim.handle->ready_rows.fetch_add(1, std::memory_order_release);

  // 通知对应 slot driver：可能有新行 ready，也可能 batch 已满需要 seal。
  slot_runtime(rt, claim.handle->slot).notice.notify_one();
}
```

### 7.1 为什么不在这里 `co_await batch_complete`

因为从 0 开始设计时，我们更想保留“continuation 可迁移”这个特性。

如果这里直接 `co_await` 等待 batch 完成，那么 continuation 会天然绑回当前 sticky task 的 scheduler，这与“任意搜索线程可恢复”冲突。

所以更自然的写法是：

- 搜索 worker 把 frame 挂到 row 上。
- 自己立刻返回 worker loop。
- 等 D2H 完成后，由 slot driver 把 frame 投递回高优先级恢复队列。

这比“一个挂起中的 playout coroutine”更接近 v1 真正冻结的调度语义。

## 8. open batch claim：从 0 开始的更自然版本

这一版不再使用“全局环形 handle + 全局 cur_hid 扫描”的写法，而改为“按 slot 维护 open batch”。

原因：

- slot 选择本来就是 timeline 驱动的。
- reservation / reconcile 也天然是 slot 维度的。
- 把 open batch 直接挂在 slot 上，所有权更清晰。

```cpp
struct ClaimResult {
  BatchHandle*   handle = nullptr;
  std::uint16_t  row    = 0;
};

ClaimResult claim_open_row(Runtime& rt, SearchFrame& frame) {
  SlotRuntime& slot = pick_best_slot_from_timeline(rt);

  while (true) {
    BatchHandle* h = slot.open_batch.load(std::memory_order_acquire);

    if (h == nullptr) {
      BatchHandle* fresh = slot.acquire_batch();
      fresh->state.store(BatchState::Open, std::memory_order_relaxed);
      fresh->claimed_rows.store(0, std::memory_order_relaxed);
      fresh->ready_rows.store(0, std::memory_order_relaxed);
      fresh->sealed_rows.store(0, std::memory_order_relaxed);
      fresh->remaining_consumers.store(0, std::memory_order_relaxed);
      fresh->slot = slot_id(slot);

      if (!slot.open_batch.compare_exchange_strong(
              h, fresh, std::memory_order_acq_rel, std::memory_order_acquire)) {
        slot.recycle_batch(fresh);
        continue;
      }

      h = fresh;
    }

    // 先抢一个 row。
    std::uint16_t row =
        h->claimed_rows.fetch_add(1, std::memory_order_acq_rel);

    if (row < max_batch_for(slot)) {
      // 刚好抢到最后一个位置，则负责 seal。
      if (row + 1 == max_batch_for(slot)) {
        try_seal_batch_and_reserve(rt, slot, *h, max_batch_for(slot));
      }
      return ClaimResult{h, row};
    }

    // 说明这个 batch 已经没有位置了，撤销本次无效 claim 的抽象意图：
    // 真正实现里这里不该靠“超发后发现满了”，而应该把 claimed_rows 的上界
    // 合并进 CAS / fetch_add 方案里。这里为了讲控制流，省略细枝末节。
    //
    // 关键抽象只有一个：claim row 与 seal 判定必须是同一个原子协议的一部分。
    help_rotate_open_batch(slot, h);
  }
}
```

### 8.1 关键约束

这里真正要冻结的是：

- “这个 batch 还能不能接收 claim”
- “我 claim 到的是哪一行”
- “是否需要由我来完成 seal”

必须属于同一个并发协议。

具体是 lock、CAS 还是别的做法，不是 v1 的关注点。

## 9. seal / publish / recycle：slot driver 常驻 task

这里采用“每个 slot 一个常驻 driver”的版本。

### 9.1 常驻 driver 的启动方式

```cpp
auto slot_driver(Runtime& rt, SlotRuntime& slot) -> exec::task<void> {
  while (true) {
    co_await slot.notice.async_wait([&] {
      BatchHandle* h = slot.open_batch.load(std::memory_order_acquire);
      return should_launch_now(rt, slot, h);
    });

    BatchHandle* h = slot.open_batch.load(std::memory_order_acquire);
    if (h == nullptr) {
      continue;
    }

    // idle seal：batch 尚未满，但 slot 已经应该尽快起飞。
    std::uint16_t claimed =
        h->claimed_rows.load(std::memory_order_acquire);
    if (claimed == 0) {
      continue;
    }

    try_seal_batch_and_reserve(rt, slot, *h, claimed);

    // 只有 seal 成功后，sealed_rows 才固定。
    std::uint16_t sealed =
        h->sealed_rows.load(std::memory_order_acquire);

    // 从 0 开始设计时，更简洁的协议是：
    // - 搜索侧发布 ready_rows；
    // - driver 等 ready_rows == sealed_rows；
    // - 然后一次性做该 batch 的 H2D / infer / D2H。
    //
    // 如果后续实测需要继续做 row-range streaming，
    // 可以在不改变 ownership 的前提下把这里扩成分段 H2D。
    co_await slot.notice.async_wait([&] {
      return h->ready_rows.load(std::memory_order_acquire) == sealed;
    });

    h->state.store(BatchState::Inflight, std::memory_order_release);

    run_h2d(*h, sealed);
    run_infer(*h, sealed);
    run_d2h(*h, sealed);

    // 结算顺序冻结。
    update_gpu_estimate(rt, slot, *h, sealed);
    reconcile_gpu_timeline(rt, slot);
    update_search_nn_target_num(rt);

    // 如果 target 前移导致 root gate 重新打开，需要唤醒搜索平面。
    if (can_issue_new_root(rt.credits)) {
      rt.search_notice.notify_all();
    }

    // 结果发布：把 frame 投递回高优先级恢复队列。
    h->remaining_consumers.store(sealed, std::memory_order_release);
    h->state.store(BatchState::Published, std::memory_order_release);

    for (std::uint16_t row = 0; row < sealed; ++row) {
      SearchFrame* frame = h->rows[row].frame;
      rt.ready_q.push(frame);
    }
    rt.search_notice.notify_all();

    // 当前 open batch 已经 seal 并完成，不再是 open 入口。
    // 真正回收要等最后一个消费者 post_process 结束。
    clear_if_current_open(slot, h);
  }
}
```

同样地，这里也省略了 stop 分支；实际实现中应由 `slot.notice.async_wait(...)` 在 stop 时返回停止完成，让 driver 自然退出。

### 9.2 解释

这段代码体现的是“从 0 开始的 stdexec 版 batch driver”，而不是“把旧 `infer_coro()` 改写成 sender”。

关键思想是：

- driver 本身是一个有明确 scheduler 归属的常驻 task。
- 它等待 slot 级事件，而不是每个 batch 临时 spawn 一个 adhoc runtime。
- publish 只负责把 frame 重新投递给搜索平面，不吞掉 `post_process()` 的 ownership。

## 10. seal 协议

```cpp
void try_seal_batch_and_reserve(
    Runtime& rt,
    SlotRuntime& slot,
    BatchHandle& h,
    std::uint16_t sealed_rows) {

  BatchState expected = BatchState::Open;
  if (!h.state.compare_exchange_strong(
          expected,
          BatchState::Sealed,
          std::memory_order_acq_rel,
          std::memory_order_acquire)) {
    return;
  }

  h.sealed_rows.store(sealed_rows, std::memory_order_release);

  // reservation 只能在 Open -> Sealed 的获胜者手里做一次。
  reserve_gpu_timeline(rt, slot, sealed_rows);
}
```

### 10.1 这比 `seal bool + 外部判断` 更好的地方

- `Open -> Sealed` 本身就是一次唯一状态转换。
- timeline reservation 天然挂在这次唯一转换上。
- 不需要额外解释“谁来保证 reserve 只做一次”。

## 11. 启动与生命周期

```cpp
auto boot(Runtime& rt) -> void {
  // 1. 启动搜索 worker。
  for (int i = 0; i < num_search_threads(rt); ++i) {
    auto sched = rt.search_pool.get_scheduler_on_thread(i);

    // starts_on: 把这个长期 task 的启动点固定到指定搜索线程。
    rt.scope.spawn(ex::starts_on(sched, search_loop(rt, i)));
  }

  // 2. 启动每个 slot 的串行 driver。
  for (SlotRuntime& slot : rt.slots) {
    auto sched = slot.ctrl_ctx.get_scheduler();
    rt.scope.spawn(ex::starts_on(sched, slot_driver(rt, slot)));
  }
}

auto shutdown(Runtime& rt) -> void {
  // 通知所有常驻任务退出。
  rt.scope.request_stop();

  // 唤醒所有可能睡着的 worker / driver。
  rt.search_notice.notify_all();
  for (SlotRuntime& slot : rt.slots) {
    slot.notice.notify_all();
  }

  // 等全部后台任务离场。
  ex::sync_wait(rt.scope.on_empty());
}
```

### 11.1 为什么这里用 `async_scope`

因为这是核心子系统，不适合 `exec::start_detached(...)`。

`start_detached` 的默认语义是：

- 没有 join
- 没有统一 stop
- 错误通常直接 terminate

而这里我们明确需要：

- 统一 stop
- 等所有后台任务退出
- 生命周期可控

所以 `exec::async_scope` 是更稳妥的 stdexec 原生选项。

## 12. 需要自己实现的 native primitives

从 0 开始用 stdexec，并不等于“所有东西都必须来自库内置”。

真正合理的做法是：

- 让 stdexec 管 execution context、sender 组合与生命周期。
- 对业务强相关的等待点，自己提供轻量的原生 sender。

本方案最需要的就是两个 primitives：

### 12.1 `Notice::async_wait(pred)`

职责：

- 在 predicate 已成立时同步完成。
- 否则挂起等待者。
- `notify_*()` 时重新检查 predicate，成立则完成。
- 必须尊重 stop token。

它更像一个“带 predicate 的 eventcount sender”，而不是普通 `condition_variable` 包装。

### 12.2 `SearchReadyQueue`

职责：

- MPMC intrusive queue。
- steady-state 不分配内存。
- 队列入队后负责触发 `search_notice.notify_one()/notify_all()`。

这里不要把恢复工作做成 `exec::any_sender_of<>` 入队。
原因很简单：

- frame 是固定形状、可复用、可池化的。
- sender 图入队要么引入 type erasure，要么把模板状态散得到处都是。
- 对这个场景来说，frame 指针就是最便宜、最清晰的 continuation 表示。

## 13. 这套 stdexec 方案里哪些地方最符合“零成本抽象”

### 13.1 sender 只用在真正的异步边界

异步边界包括：

- worker 等待新工作
- slot driver 等待 seal/ready
- 系统启动与关闭

而不包括：

- 每一次树下降
- 每一次 backprop
- 每一次 frame 小步推进

这能显著减少中间 sender 状态和模板层数。

### 13.2 不用 `any_sender`

热路径全部使用具体类型：

- `exec::task<void>` 只用于常驻任务
- `SearchFrame*` 用于 continuation
- `BatchHandle*` 用于 batch 生命周期

这比把 continuation 存成 type-erased sender 更便宜，也更容易内联。

### 13.3 不用 `start_detached`

`async_scope + starts_on(...)` 的组合更清楚：

- 任务在哪里跑
- 谁拥有它
- 何时停止
- 何时 join

### 13.4 sticky task 只用在“应该 sticky”的地方

`exec::task` 的 sticky scheduler 语义非常适合：

- 常驻搜索 worker
- 常驻 slot driver

但不适合：

- 需要跨搜索线程迁移的 playout continuation

所以 continuation 单独用 frame 状态机表达，这不是“退化”，而是顺着 stdexec 语义做出的更优切分。

## 14. 与 v0 写法最重要的差异

如果把 v0 的 asyncio 风格直译到 stdexec，最容易犯两个错：

1. 想把每个 playout continuation 都保留成一个挂起中的 task。
2. 想把现有通知点都先包成 sender，再维持原有控制流形状。

这两个方向都不是本版建议。

本版建议是：

- 用 stdexec 原生 execution context 承载长期运行的主体。
- 用显式 frame 状态机承载 migratable continuation。
- 用极少数 native sender primitives 表达真正的等待点。

换句话说，stdexec 在这里主要负责“跨 execution context 的组织方式”，而不是“把所有业务步骤都抬成 sender”。

## 15. 最终建议

如果后续真的落代码，建议按下面顺序实现：

1. 先实现 `Notice` 与 `SearchReadyQueue` 这两个 native primitives。
2. 再实现 `search_loop()` + `slot_driver()` 两个常驻 task。
3. 然后把 playout 改成显式 `SearchFrame` 状态机。
4. 最后再决定 sealed 后是否要继续细化成 row-range streaming H2D。

这样做的好处是：

- 先把 execution topology 搭稳。
- 再把热路径 state machine 嵌进去。
- 最后才做数据面细化，不会在运行时形状上反复返工。

这也是最符合 v1 目标的 stdexec 起步方式。
