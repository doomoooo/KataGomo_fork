# 计划

本文档用于在 `plan/v0.md` 的基础上，基于 2026-03 的工具链调研和对 `third_party/stdexec` 源码的直接阅读，重新定义 TensorRT 调度与搜索侧协程化架构。

## plan_v1

状态：重写版（以 `v0` 约束为准，按 `stdexec` 实际语义修正）

### 1. 从 v0 继承且必须保留的约束

以下内容不是本版新决策，而是从 `v0` 直接继承下来的硬约束：

- 优先级仍然是端到端最高吞吐，而不是抽象纯洁性。
- TensorRT-only fast path 仍然允许存在。
- backend-specific 复杂度可以存在，但必须局部化，且所有权、同步方式、生命周期必须明确。
- 长期目标仍然是从固定搜索线程模型走向按需求驱动的 playout 调度。
- 长尾事实已经固化：edge-visit 冲突会让 request 产出出现明显长尾，GPU 可能等待单个 CPU 长尾路径。

因此，`v1` 不再重新论证 fixed-thread 模型是否足够好，而是直接回答：

- 在 `stdexec` 世界观下，最终模块应该怎么拆。
- 哪些边界该用 sender/scheduler 表达，哪些边界仍然是项目内 runtime。
- TensorRT fast path 应该如何和多线程协程调度对接，而不重新引入线程耦合。

### 2. 本版对上一版的关键修正

在直接阅读 `stdexec` 源码后，上一版里有几处需要明确纠正：

- `stdexec` 不是“一套现成的项目协程运行时”
  - 它首先是 sender/scheduler 模型和一组算法。
  - `exec` 命名空间提供一些很有用的扩展，如 `exec::task`、`exec::async_scope`、`exec::static_thread_pool`。
  - 但搜索侧最终仍然需要项目自己的 `PlayoutRuntime` 和 TensorRT 专用 runtime。

- `Receiver` / `OperationState` 不应成为模块公共接口
  - 在 `stdexec` 里，它们是实现 sender 的底层机械结构。
  - 模块之间的公共边界应暴露成：
    - 普通值类型
    - sender-returning API
    - 必要时的 `exec::task`
  - 而不是把 receiver/opstate 作为系统级对象设计出来。

- `NNRequest` 不应再携带 continuation / handle / token
  - 这在 callback 世界里是自然做法，但在 `stdexec` 里不是最佳边界。
  - continuation 应由 sender/receiver 连接时形成的 operation state 持有。
  - 因此搜索侧与 NN 层之间更合理的接口是：
    - `NNRequest` 只描述“要算什么”
    - `submit(NNRequest)` 返回 sender，完成时产出 `NNEvalResult`

- `exec::task` 的调度语义必须按真实源码理解
  - `exec::task` 是 coroutine type，同时也是 sender。
  - 它默认是 scheduler-sticky 的。
  - 在 `exec::task` 里，`co_await schedule(sched)` 不等于“把当前 coroutine 迁移到这个 scheduler 上继续跑”。
  - 真正的显式迁移原语是 `exec::reschedule_coroutine_on(sched)`。
  - 这会直接影响 playout coroutine 应如何实现 CPU worker 间迁移与让出。

这是本版重写的基础。

### 3. 第一步结论：工具链与依赖

#### 3.1 语言标准

结论：

- 主开发基线升级到 `C++20`。
- 不再以 `C++17` 作为主开发基线。

理由：

- `stdexec` 需要 `C++20`。
- 这条线的核心问题是调度语义、挂起/恢复语义和 sender/scheduler 组合语义，直接使用标准协程与 `stdexec` 的组合最自然。

#### 3.2 编译器基线

结论：

- Linux / TensorRT 主开发基线直接对齐本地 `LLVM/Clang 22.1.1`。
- 兼容检查通道对齐 `GCC 15.2`。
- `Clang 20.x` 视为可接受下限，但不再作为首选目标。

原因：

- 当前 TensorRT-only 路径本身不依赖 `nvcc` 编译，所以没有必要为了 CUDA 语言工具链压低主机侧编译器版本。
- `stdexec` 与 coroutine / concepts / sender 组合会高度依赖编译器前端质量和历史 bug 情况。
- 因此，这条线应该主动使用更高版本编译器，而不是贴着“最低可编译版本”前进。

当前工程状态（2026-03-21）：

- `cpp` 构建基线已切到 `C++20`。
- `build.sh` 已支持 `--bootstrap-llvm`，会把官方 `LLVM/Clang 22.1.1` 预编译包放到仓库本地路径。
- `build.sh` 现在会优先选本地高版本 `Clang`，并自动接入 `ld.lld / llvm-ar / llvm-ranlib`，避免 `IPO/LTO` 误走 `LLVMgold.so` 插件路径。
- 本地实际验证已经完成：`TensorRT + stdexec` 路径可在 `LLVM/Clang 22.1.1` 下成功构建，`katago version` 验证通过。

#### 3.3 stdexec 依赖策略

结论：

- 主机侧异步模型采用 `stdexec`。
- 更准确地说，是：
  - `stdexec::` 提供标准 sender/scheduler 算法与概念
  - `exec::` 提供项目实际会用到的扩展能力
- `nvexec` 不进入这条 TensorRT 设计主线。

当前本地依赖基准：

- `third_party/stdexec`
- 当前快照：`46ca0458a9806f63cde1c3bba76a2ec720974c00`

### 4. 从 stdexec 源码直接得到的设计结论

#### 4.1 stdexec 负责的是什么

对本项目真正有价值的，不是“它提供了一个现成 runtime”，而是：

- 一套 sender/scheduler 协议
- 一组组合算法
- 一套把 callback-style completion 改写成 sender completion 的统一语言
- 一条把 coroutine 与 sender 连接起来的方式

因此，本项目应把 `stdexec` 当作：

- 异步边界的协议层
- 组合逻辑的公共语言
- coroutine 与调度系统之间的桥

而不是把它当作“搜索运行时已经写好了，只要接进来即可”。

#### 4.2 这条线真正会用到的 stdexec 能力

本项目最相关的能力是：

- `stdexec::schedule`
- `stdexec::starts_on`
- `stdexec::continues_on`
- `stdexec::then`
- `stdexec::let_value`
- `stdexec::when_all`
- `stdexec::sync_wait`
- `stdexec::get_scheduler`
- `stdexec::get_stop_token`

以及 `exec::` 扩展中的：

- `exec::task`
  - coroutine 与 sender 的桥接点

- `exec::async_scope`
  - 用于追踪一组顶层异步任务的生命周期与 stop 传播

- `exec::static_thread_pool`
  - 当前阶段可作为可用 CPU scheduler
  - 但不应直接被认定为最终 playout 调度策略

- `exec::single_thread_context`
  - 更适合作为测试与确定性验证工具，而不是生产调度核心

- `exec::reschedule_coroutine_on`
  - 在 `exec::task` 内显式迁移 coroutine 所在 scheduler 的原语

#### 4.3 对 exec::task 的正确理解

`exec::task` 对这条线非常关键，因为它决定了 playout coroutine 的自然写法。

它的关键语义是：

- `exec::task<T>` 既是 coroutine type，也是 sender。
- 它是 scheduler-sticky 的。
- 子 coroutine 默认继承父 coroutine 的 scheduler 语义。
- 在 `exec::task` 中 `co_await` 一个 sender 时，如果该 sender 不是“在当前 scheduler 上开始并在同一 scheduler 上完成”，`task` 的 `await_transform` 会把它包成 `continues_on(current_scheduler)` 再等待。

这意味着：

- 如果 `PlayoutTask` 运行在 CPU playout scheduler 上，那么它 `co_await` 一个 TensorRT completion sender 后，应恢复到自己的 CPU scheduler 上继续修改搜索树。
- 这正是我们想要的语义。
- 因而，搜索侧不需要把 continuation handle 塞进 `NNRequest`。
- 更合理的做法是让 NN 层返回 sender，然后让 `PlayoutTask` 直接 `co_await` 它。

同时必须注意：

- `co_await stdexec::schedule(other_scheduler)` 不能作为“迁移当前 coroutine 到别的 worker”的统一做法。
- 如果需要显式改变 coroutine 之后继续运行的 scheduler，应使用 `exec::reschedule_coroutine_on(other_scheduler)`。

这是本版最重要的语义修正之一。

### 5. 最终架构

本版仍然保持五层，但重新定义每层的边界，使其符合 `v0` 目标，也符合 `stdexec` 的真实语义。

1. `SearchTreeCore`
2. `PlayoutRuntime`
3. `NNRequestLayer`
4. `TensorRTRuntime`
5. `DemandController`

这里的关键不是“再造一套抽象”，而是把每一层分别回答清楚：

- 哪些东西是普通值类型
- 哪些 API 返回 sender
- 哪些东西是 coroutine
- 哪些东西仍然是 backend-specific 状态机

#### 5.1 SearchTreeCore

职责：

- 维护树语义
- child 选择
- virtual loss / edge-visit 语义
- expansion
- eval 回填后的统计更新
- 图搜索一致性

它不负责：

- 线程池
- coroutine 生命周期
- TensorRT buffer / slot / batch
- callback / continuation / receiver

对外接口不应再是“同步跑完整个 playout”，而应是一次次推进：

```text
PlayoutStep step(PlayoutCursor&, SearchScratch&)
apply_eval(PlayoutCursor&, NNEvalResult&&)
finish(PlayoutCursor&, PlayoutTerminal&&)
```

其中 `PlayoutStep` 应是高层语义枚举，而不是 scheduler 细节：

- `Continue`
- `NeedEval`
- `Retry`
- `Finish`

#### 5.2 PlayoutRuntime

这是搜索协程运行时本体。

它负责：

- 顶层 playout 工作的注入与回收
- `exec::task` 生命周期
- CPU worker 调度
- 显式让出与显式迁移
- stop / cancellation 传播
- 与 `DemandController` 协同决定当前有多少 in-flight playout

它对外的核心抽象不应再是：

- `Receiver`
- `OperationState`
- continuation queue

而应是：

- `PlayoutTask`
- `PlayoutScheduler`
- 顶层 `exec::async_scope`
- 一组 sender-returning runtime API

更具体地说：

- 单次 playout 应实现为 `exec::task<void>` 或 `exec::task<PlayoutOutcome>`
- 顶层注入形式应类似：
  - `scope.spawn(stdexec::starts_on(playout_scheduler, run_playout(...)))`
- 如果需要在 CPU worker 间显式迁移，则在 task 内使用：
  - `co_await exec::reschedule_coroutine_on(playout_scheduler)`

这层内部可以先用 `exec::static_thread_pool` 验证语义，但最终不应把 `static_thread_pool` 当作长期设计本身。

长期结论是：

- 我们需要项目自己的 `PlayoutScheduler`
- 但它应建模 `stdexec::scheduler`
- 而不是再自造一套与 `stdexec` 平行的调度协议

#### 5.3 NNRequestLayer

这是搜索与后端之间的协议层。

职责：

- 定义 `NNRequest`
- 定义 `NNEvalResult`
- 定义请求提交流程的公共 sender API
- 定义 host 侧特征物化与请求所有权边界

最重要的修正是：

- `NNRequest` 不再包含 continuation handle
- `NNRequest` 不再知道任何 `PlayoutTask` 内部状态
- `NNRequest` 只描述“要计算什么”

这一层更自然的接口形态应是：

```text
sender auto submit(NNRequest)
```

其 completion 应表达为：

- `set_value(NNEvalResult)`
- `set_error(std::exception_ptr)`
- `set_stopped()`

这样 `PlayoutTask` 可以直接：

```text
NNEvalResult result = co_await request_layer.submit(std::move(req));
```

而 coroutine 恢复语义由 `exec::task` + sender await 语义保证，不再需要手写 continuation token。

#### 5.4 TensorRTRuntime

这一层只负责 TensorRT 专属执行。

职责：

- ready queue
- slot 管理
- row / batch buffer 生命周期
- H2D / infer / D2H 提交流程
- 输出解包
- 将 backend completion 翻译成 sender completion

它不应负责：

- 搜索树语义
- board/history 语义
- playout coroutine 生命周期

这一层内部可以继续高度 backend-specific。

允许存在的 TensorRT-only fast path：

- row 特征直接进入 TensorRT 专用 staging / pool
- backend 专属 batch builder
- backend 专属 copy-elision 策略

但必须满足两个条件：

- 这些复杂度被收束在 `NNRequestLayer + TensorRTRuntime` 边界内
- 搜索侧看见的仍然是 `submit(NNRequest) -> sender<NNEvalResult>`

也就是说，TensorRT fast path 可以侵入 request 的内部存储策略，但不应重新穿透到搜索 coroutine 边界。

#### 5.5 DemandController

职责：

- 决定当前应保有多少 in-flight playout
- 决定当前应保有多少 ready / nearly-ready NN work
- 根据 GPU 需求与长尾事实调节注入速率

它消费的不是“要不要重新验证长尾”，而是已经承认长尾存在后的控制量：

- 当前 TensorRT 排队深度
- 未来短时间 slot 空闲信息
- 当前 in-flight playout 数
- 当前 in-flight NN 请求数
- 当前 ready request 数

它输出的是 runtime 控制信号：

- 是否继续发放新的 playout token
- 当前目标 in-flight playout 上限
- 当前目标 request 库存区间

它不直接管理 TensorRT buffer，也不直接修改树。

### 6. 关键接口草案

为了让模块边界更直观，本版推荐以下接口形态。

#### 6.1 SearchTreeCore 到 PlayoutRuntime

核心结果类型应类似：

```text
Continue
NeedEval { FeatureSpec feature_spec, LeafContext leaf }
Retry { RetryReason reason }
Finish { PlayoutTerminal terminal }
```

含义：

- `SearchTreeCore` 只说“下一步语义是什么”
- `PlayoutRuntime` 决定如何调度

#### 6.2 PlayoutRuntime 到 NNRequestLayer

公共接口应类似：

```text
NNRequest req = materialize_request(feature_spec, leaf, ...);
NNEvalResult eval = co_await nn_request_layer.submit(std::move(req));
```

这里的关键点：

- `materialize_request` 发生在显式边界上
- request 生命周期明确
- 没有 continuation handle 穿过这个边界

#### 6.3 NNRequestLayer 到 TensorRTRuntime

内部接口可以 backend-specific，但公共要求是：

- `NNRequest` 进入 TensorRT 层后，其所有权转移规则明确
- TensorRT completion 最终必须回到 sender completion 语义
- 不能让搜索层借用 open batch 内部 buffer

如果后续要减少一次 host-side copy，也应通过：

- 新的 request storage class
- 新的 TensorRT-specific request representation

来做，而不是通过隐式别名关系把搜索层和 batch builder 绑死。

### 7. 最终运行方式

本版推荐的运行方式如下：

1. `DemandController` 决定当前还需要多少新的 playout 尝试。
2. `PlayoutRuntime` 通过顶层 `exec::async_scope` 发射对应数量的 `PlayoutTask`。
3. 每个 `PlayoutTask` 在 `PlayoutScheduler` 上运行，并循环调用 `SearchTreeCore::step()`。
4. 遇到 `NeedEval` 时，task 构造 `NNRequest`，然后 `co_await nn_request_layer.submit(req)`。
5. TensorRT 完成后，sender 发出 completion，`PlayoutTask` 恢复到自己的 scheduler 上继续推进。
6. 遇到 `Retry` 时，runtime 可选择：
   - 立即重试
   - `co_await exec::reschedule()` / scheduler-specific yield
   - 结束本次 task，由控制器重新投放新的尝试
7. 遇到 `Finish` 时执行回填并结束 task。

这里最重要的不是“协程语法本身”，而是：

- 搜索语义和调度语义已经分层
- NN completion 不再通过线程身份恢复
- TensorRT fast path 仍然能局部保持高性能

### 8. 当前明确不做的事

- 不把 `Receiver` / `OperationState` 提升为系统公共抽象。
- 不把 `NNRequest` 设计成携带 continuation handle 的对象。
- 不把 `exec::static_thread_pool` 直接认定为最终 playout 调度策略。
- 不假设 `co_await schedule(sched)` 就能完成 coroutine 迁移。
- 不为了“看起来纯粹”而否定 TensorRT-only fast path。
- 不重新回到“先证明长尾是否存在”的路线。

### 10. 本版结论

本版的核心结论只有四条：

1. `v1` 继续继承 `v0` 的性能优先与 TensorRT-only fast path 前提，不再为抽象整洁牺牲吞吐。
2. `stdexec` 应作为异步协议层和组合语言；项目仍然需要自己的 `PlayoutRuntime` 与 `TensorRTRuntime`。
3. `NNRequest` 不应携带 continuation；更合理的边界是 `submit(NNRequest) -> sender<NNEvalResult>`，让 `PlayoutTask` 直接 `co_await`。
4. `exec::task` 的 sticky scheduler 语义和 `reschedule_coroutine_on` 原语必须成为搜索协程设计的基础规则，而不是事后补丁。
