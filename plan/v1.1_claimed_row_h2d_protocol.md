# v1.1 Claimed Row / H2D 协议

本文档只讨论一件事：

- search thread 在 `claim row -> pre_process -> row ready publish` 这一段，
- 与 slot driver 在 `H2D 提交 / seal / launch` 这一段，
- 围绕“谁来发布 ready 前缀、谁来提交 H2D、谁来决定立即 seal”之间的协议。

本文档的目标是把这块交互单独定死，不让它继续散落在总文档里。

## 0. 核心判断

这里冻结三条判断：

1. 连续 ready 前缀的天然归约点，在 search thread 的 `pre_process()` 完成之后。
2. search thread 不发布 `[low, high)`，也不发布排队的 `high` 消息；它只维护共享的 `ready_prefix`。每个 batch 的 driver coroutine 自己用 `[h2d_issued_prefix, ready_prefix)` 推导下一段 H2D。
3. 同一 slot 上允许“前一 batch 尚未完成，后一 batch 已开始 claim row”；因此协议采用“一个 `BatchHandle` 对应一个 `serve_batch(h)` coroutine”，而不是一个 global loop 去 demux 全部 batch 事件。

也就是说：

- ready frontier 的“发现”尽量靠近 row ready 的发生点。
- H2D 的“真正提交”仍然由 slot driver 串行拥有。
- 不同 batch 可以并存，但它们各自有自己的 driver coroutine 与局部水位。

## 1. 要解决的具体问题

如果沿用“一个 slot 一个 global driver loop”的写法，那么一旦出现：

- batch A 还在等自己的 H2D / infer / D2H completion，
- batch B 已经开始 claim row 并推进 ready，

driver 就必须同时回答：

- 这个 ready 推进属于哪个 batch
- 这个 H2D done 属于哪个 batch
- 这个 infer / D2H completion 属于哪个 batch
- 当前应该尝试 `gpu idle -> seal` 的 open batch 是哪个

这样协议的复杂度就会从“row ready / H2D / seal”本身，膨胀成“全局事件 demux + 多 batch 状态表”。

本文档采用的结论是：

- search thread 只负责把本 batch 的 `ready_prefix` 推到最新值，并定点唤醒这个 batch 对应的 driver coroutine。
- 每个 batch 的 driver coroutine 只追踪自己的 `h2d_issued_prefix / last_h2d / infer / d2h`。
- completion path 只保留一个跨 batch 动作：当旧 batch 的完成让 GPU 可能 idle 时，尝试对当前 open batch 做 driver-side seal，并唤醒它自己的 coroutine。

这里的 `GPU idle` 专指：

- 该 slot 所属的 GPU 执行上下文已经没有在飞的 H2D / infer / D2H 工作。
- 它不是指“这个 slot 上没有 open batch”，两者在语义上是不同的。

## 2. 所有权分工

### 2.1 search thread 拥有的职责

- 决定一次 playout 需要 NN。
- 先递增 `nn_issue_current`。
- claim row。
- 如果这次 claim 让 batch 到达上界，则由 search thread 当场完成 `Open -> Sealed`，并负责 reservation。
- 执行 `pre_process()`。
- 在 handle-local 临界区内发布 `ready[row] = true`。
- 尝试推进 `ready_prefix`。
- 如果自己这次推进了 `ready_prefix`，就直接唤醒这个 batch 对应的 driver coroutine。

### 2.2 batch-local driver coroutine 拥有的职责

- 每个 live `BatchHandle` 对应一个 `serve_batch(h)` coroutine。
- 拥有这个 batch 的 `h2d_issued_prefix` 与 `last_h2d`。
- 在被唤醒后，用 `[h2d_issued_prefix, ready_prefix)` 直接推导下一段精确 H2D。
- 当 `sealed_rows != 0` 且 `h2d_issued_prefix == sealed_rows` 时，等待该 batch 的最后一次 H2D 完成并发起 infer launch。
- 随后等待这个 batch 自己的 infer / D2H completion，并完成 batch 收尾。

### 2.3 slot-local 协调层拥有的职责

- 在 batch 进入 `Open` 时，把它的 `serve_batch(h)` spawn 到所属 slot 的 single-thread driver scheduler 上。
- 维护“当前 open batch”这一 slot-local 指针。
- 当旧 batch 的某个 completion path 可能让 GPU 进入 idle 时，尝试对当前 open batch 执行 driver-side seal。
- 如果 idle seal 成功，直接唤醒被 seal 的那个 batch coroutine。
- 因为同一 slot 的所有 batch coroutines 都跑在同一个 single-thread scheduler 上，GPU 提交顺序仍然天然串行。

### 2.4 不再让 slot driver 负责的事情

- 不再维护 slot-global 的 `H2DRange` 队列。
- 不再用一个 global loop demux 同一 slot 上所有 batch 的 H2D / infer / D2H 事件。
- 不再把“从零反复扫描下一段 ready range 是什么”当作 steady-state 主逻辑。

## 3. 需要冻结的状态

这份协议不追求 lock-free publish。

这里的判断是：

- `pre_process()` 本身已经是重操作。
- 在它结束后进入一个很小的 handle-local 临界区，成本是可控的。
- 这个临界区可以把大量原本分散的 shared state 折叠掉。

因此，本协议采用：

- 一个 handle-local mutex 串行化 `claim / publish-ready-prefix / seal`
- 一个 batch-local 的 driver wake handle，承接 search thread 对该 batch coroutine 的直接唤醒

```cpp
struct BatchDriverHandle {
  Notice notice;
};

struct BatchHandle {
  Mutex                      mu;
  std::uint16_t              claimed_rows = 0;
  // 0 表示 Open；非 0 表示已经 Sealed，且值就是固定下来的 batch 大小。
  std::uint16_t              sealed_rows = 0;

  // 最大前缀 [0, ready_prefix) 满足“所有 row 都 ready”。
  // 只在 handle.mu 保护下推进。
  std::uint16_t              ready_prefix = 0;

  SlotId                     slot{};
  BatchDriverHandle*         driver = nullptr;
  // 0/1 ready 标记。这里直接用 uint8_t，避免 vector<bool> 特化。
  std::vector<std::uint8_t>  ready;
  HostStagingBuffer          host_mem;
};

struct DriverBatchState {
  std::uint16_t         h2d_issued_prefix = 0;
  Event                 last_h2d = {};
};
```

其中：

- `claimed_rows` / `sealed_rows` / `ready_prefix` / `ready[]` 的所有者是“handle.mu 保护下的 shared state”。
- `h2d_issued_prefix` / `last_h2d` 的所有者是“这个 batch 自己的 driver coroutine 局部状态”。
- `driver` 只是这个 batch 的唤醒入口；具体 coroutine task 对象由 slot runtime 持有。

这几个水位必须满足：

- 对每个 batch 都有 `h2d_issued_prefix <= ready_prefix <= claimed_rows`
- `sealed_rows == 0 || sealed_rows == claimed_rows`

## 4. Search Thread 协议

### 4.1 pre_process 完成后的固定顺序

当一个 playout 需要 NN 时，搜索侧顺序固定为：

1. `nn_issue_current.fetch_add(1)`
2. `row = claim_row()`
3. 对 `row` 执行 `pre_process()`
4. 进入一个很小的 publish 临界区，写入 `ready[row] = true`
5. 尝试推进 `ready_prefix`
6. 如果自己推进成功，则直接唤醒这个 batch 的 driver coroutine

### 4.2 为什么 search thread 不再显式生成 range 或 high 消息

在新的模型里，search thread 在 row-ready 现场最重要的工作不是“构造一个命令对象”，也不是“排队发送一个新的 high 值”，而是：

- 及时把 `ready_prefix` 推到正确位置
- 把“这个 batch 出现了新的可提交前缀”这件事定点通知给对应 coroutine

因为一旦某个 batch 的 driver coroutine 自己拥有：

- 这个 batch 的 `h2d_issued_prefix`
- 这个 batch 的最新 `ready_prefix`

那么它就能在本地无歧义地推出：

- 下一段 exact H2D range 就是 `[h2d_issued_prefix, ready_prefix)`

所以这里冻结的不是“search thread 必须 materialize 一个 `H2DRange` 对象”或“必须按序发布 high 事件”，而是：

- search thread 必须在 row-ready 现场把 `ready_prefix` 归约正确
- 并且只唤醒正确的那个 batch coroutine

### 4.3 `claim_row()` 的协议

`claim_row()` 的规则固定为：

```cpp
auto claim_row(Runtime& rt, BatchHandle& h) -> std::uint16_t {

  std::lock_guard lk(h.mu);

  if (h.sealed_rows != 0) {
    throw RetryAnotherHandle{};
  }

  std::uint16_t row = h.claimed_rows++;

  if (h.claimed_rows == max_batch_for(h.slot)) {
    h.sealed_rows = h.claimed_rows;
    // 协议要求 reservation 与 sealed_rows 的可见化属于同一次 seal。
    reserve_gpu_timeline(rt, slot_runtime(rt, h.slot), h.sealed_rows);
  }

  return row;
}
```

这段规则冻结的是：

- `batch full` 不是“叫醒某个 global driver 让它再看一眼”。
- `batch full` 由达到上界的 search thread 当场完成 seal。
- reservation 与 `sealed_rows` 的可见化属于同一次 seal。
- 因此，这个 batch 自己的 driver coroutine 之后观察到 `sealed_rows != 0` 时，可以把 reservation 视为已经完成。

### 4.4 推进 `ready_prefix` 并唤醒 batch coroutine 的算法

```cpp
void publish_row_ready_and_maybe_wake_batch_driver(
    BatchHandle& h,
    std::uint16_t row) {

  bool wake = false;

  {
    std::lock_guard lk(h.mu);

    h.ready[row] = 1;

    // 只有补到了当前前缀缺口，才有可能让 driver 获得新的 H2D 工作。
    if (row != h.ready_prefix) {
      return;
    }

    while (h.ready_prefix < h.claimed_rows &&
           h.ready[h.ready_prefix] != 0) {
      ++h.ready_prefix;
    }

    wake = true;
  }

  if (wake) {
    h.driver->notice.notify_one();
  }
}
```

这段协议冻结了两件事：

- 只有真正推进了 `ready_prefix` 的线程，才有资格唤醒这个 batch 的 driver coroutine。
- 因为 `ready_prefix` 在 `handle.mu` 内串行推进，所以它是单调不减的共享 level state，而不是按次消费的消息流。

### 4.5 这为什么不是“多做了一遍扫描”

这里的扫描不是 slot driver 在远处反复猜测 range，也不是 lock-free 原子体操。

这里的扫描是：

- 在刚刚发生 row ready 的现场，
- 在一个很小的 handle-local 临界区内，
- 以当前 `ready_prefix` 为起点，
- 尽可能把可连续推进的前缀一次性吃掉。

而 driver coroutine 醒来之后，不是再从零扫描所有 rows，而只是读取：

- 这个 batch 当前的 `ready_prefix`
- 自己已经走到哪里的 `h2d_issued_prefix`

然后直接得到下一段 `[h2d_issued_prefix, ready_prefix)`。

这意味着：

- coro 读到的 `ready_prefix` 允许跳跃，也允许与上次相同
- 但它不允许回退
- 只要 `ready_prefix` 单调不减、而 `h2d_issued_prefix` 由 coro 本地维护，就不会造成实质性错误；区别只在于多次小 H2D 可能被合并成一次更大的 H2D

## 5. Batch Driver Coroutine 协议

### 5.1 一个 `BatchHandle` 对应一个 `serve_batch(h)`

当一个 batch 进入 `Open` 时，slot runtime 要在所属 slot 的 single-thread driver scheduler 上 spawn：

- `serve_batch(rt, slot, h)`

并把这个 coroutine 的唤醒入口写到：

- `h.driver`

不同 batch 可以在同一 slot 上并存：

- batch A 可能还在等自己的 H2D / infer / D2H completion
- batch B 已经开始 claim row 并推进 `ready_prefix`

但这不再需要一个 global loop 去 demux：

- A 由 `serve_batch(A)` 管
- B 由 `serve_batch(B)` 管
- 它们都跑在同一个 slot driver scheduler 上，因此实际 GPU 提交顺序仍然串行

伪代码可以写成：

```cpp
auto serve_batch(Runtime& rt, SlotRuntime& slot, BatchHandle& h)
    -> exec::task<void> {
  DriverBatchState st{};
  std::uint16_t    sealed_rows = 0;

  while (true) {
    std::uint16_t ready = 0;

    {
      std::lock_guard lk(h.mu);
      ready       = h.ready_prefix;
      sealed_rows = h.sealed_rows;
    }

    if (ready > st.h2d_issued_prefix) {
      st.last_h2d = run_h2d(h, range(st.h2d_issued_prefix, ready));
      st.h2d_issued_prefix = ready;
      continue;
    }

    if (sealed_rows != 0 &&
        st.h2d_issued_prefix == sealed_rows) {
      break;
    }

    co_await h.driver->notice.async_wait([&] {
      std::lock_guard lk(h.mu);
      return h.ready_prefix > st.h2d_issued_prefix
          || (h.sealed_rows != 0 &&
              st.h2d_issued_prefix == h.sealed_rows);
    });
  }

  co_await wait_event(st.last_h2d);

  Event infer_done = run_infer(h, sealed_rows);
  co_await wait_event(infer_done);

  on_batch_completion_that_may_make_gpu_idle(rt, slot);

  Event d2h_done = run_d2h(h, sealed_rows);
  co_await wait_event(d2h_done);

  on_batch_completion_that_may_make_gpu_idle(rt, slot);

  notify_batch_finished(h);
}
```

这段伪代码要表达的，不是具体 API 形状，而是以下协议事实：

- 每个 batch 只等待与自己有关的唤醒和 completion
- launch 前的最后一段 H2D 判断，完全是这个 batch coroutine 的局部决策
- 不存在 slot-global 的 H2D command queue

### 5.2 driver-side idle seal 是跨 batch 的 completion helper

同一 slot 上真正需要跨 batch 协调的，只剩下一件事：

- 旧 batch 的某个 completion path 让 GPU 可能变 idle 时，
- 需要看一眼当前 open batch，
- 如有必要，为它执行 driver-side seal。

可以把这条规则写成：

```cpp
void on_batch_completion_that_may_make_gpu_idle(
    Runtime& rt,
    SlotRuntime& slot) {

  BatchHandle* open = current_open_handle_for(slot);
  if (open == nullptr) {
    return;
  }

  if (try_idle_seal_and_reserve(rt, slot, *open)) {
    open->driver->notice.notify_one();
  }
}

auto try_idle_seal_and_reserve(
    Runtime& rt,
    SlotRuntime& slot,
    BatchHandle& h) -> bool {

  std::lock_guard lk(h.mu);

  if (h.sealed_rows != 0) {
    return false;
  }
  if (h.claimed_rows == 0) {
    return false;
  }
  if (!gpu_idle_for(slot)) {
    return false;
  }

  h.sealed_rows = h.claimed_rows;
  reserve_gpu_timeline(rt, slot, h.sealed_rows);
  return true;
}
```

这段规则冻结的是：

- driver-side seal 不是 global loop 的职责，而是 completion path 上的一个帮助动作。
- 这份协议不要求把它绑死在某一个固定 completion 点；只要求“任何可能让 GPU 进入 idle 的 completion path”都可以调用它。
- 这里的 `GPU idle` 是“该 slot 对应的 GPU 执行上下文无在飞工作”，不是“slot 上已经没有 open batch”。
- 它操作的目标不是“某个正在完成的旧 batch”，而是“当前 open batch”。
- idle seal 一旦成功，必须直接唤醒被 seal 的那个 batch coroutine。

### 5.3 下一段 H2D 的推导规则

这份协议里不再定义 `H2DRange` 队列对象。

对某个 batch 来说，下一段 exact H2D 的规则固定为：

- `low = h2d_issued_prefix`
- `high = ready_prefix`
- 如果 `high > low`，就提交 `[low, high)`

也就是说：

- exact range 不是靠 global queue 保留下来
- 而是靠“search thread 已经归约好的 `ready_prefix`”和“driver coroutine 自己持有的 `h2d_issued_prefix`”在本地重建出来

因此：

- 同一个 batch 不会重复上传已经提交过的前缀
- 不同 batch 之间也不会因为共用一个 global submitted 状态而互相污染
- `ready_prefix` 是共享 level state，不是 ordered message stream；coro 每次读取的是“当前最新值”，而不是“下一条 high 消息”

### 5.4 batch 并存语义

这份协议明确允许：

- batch A 尚未完成
- batch B 已开始 claim row

搜索侧只需要保证一条：

- 不同 batch 的 `claim row` 顺序是串行的

这就已经足够，因为：

- slot 上的“当前 open batch”因此总是明确的
- 每个 batch 都有自己独立的 driver coroutine 与 `h2d_issued_prefix`
- 实际 GPU 提交顺序仍然由 slot 的 single-thread scheduler 串行化

## 6. Launch 条件

对某一个 batch 来说，infer launch 的条件固定为：

1. 这个 batch 的 `sealed_rows != 0`
2. 这个 batch 的 `h2d_issued_prefix == sealed_rows`
3. 这个 batch 自己的 `last_h2d` event 已完成

只有这三条都成立，这个 batch 的 driver coroutine 才能真正 launch infer。

这里特别说明：

- launch 等待的是“该 batch 已 seal 的整个前缀都已提交并完成 H2D”
- 不是等待某个 slot-global 的 `H2DLastDone` demux
- 也不是依赖一条额外的 post-seal flush 路径

## 7. 不变量

这个协议必须维持以下不变量：

1. `ready_prefix` 对每个 batch 都单调不减。
2. `h2d_issued_prefix` 对每个 batch 都单调不减。
3. 对每个 batch 都有 `h2d_issued_prefix <= ready_prefix <= claimed_rows`。
4. `sealed_rows == 0 || sealed_rows == claimed_rows`。
5. 每个 live batch 都有自己独立的 driver wake handle 与 driver coroutine 局部状态。
6. 同一 slot 上可以有多个 live batches。
7. 同一 slot 上所有 batch coroutines 都运行在同一个 single-thread driver scheduler 上，因此 GPU 提交顺序仍然串行。
8. search thread 不再向 slot-global queue 推 H2D 命令，也不发布排队的 high 值；它只推进 `ready_prefix` 并唤醒对应 batch coroutine。
9. `Open -> Sealed` 可以由两条路径发生，且只发生一次：
   - search thread 的满 batch seal
   - completion path 在 GPU idle 时对当前 open batch 的 idle seal
10. idle seal 成功后，必须直接唤醒被 seal 的那个 batch coroutine。
11. `nn_issue_current` 在 claim row 之前递增。

## 8. 与总文档的关系

这份文档冻结的是一个更细粒度的子协议：

- ready frontier 在哪里被归约
- H2D 由谁真正提交
- batch 并存时如何避免全局 demux
- `gpu idle` 如何跨 batch 介入 seal

- search thread 在 row ready 现场推进 `ready_prefix`
- 每个 `BatchHandle` 对应一个 batch-local `serve_batch(h)` coroutine
- 同一 slot 上可以有多个 live batches，但 GPU 提交顺序仍然串行
- 满 batch 由 search thread 当场 seal；idle seal 由 completion path 在 GPU idle 时介入
