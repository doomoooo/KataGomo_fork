# 计划

本文档冻结当前生效的总架构方向。

控制流以 [v0_pseudo.cpp](./v0_pseudo.cpp) 为准；本文只负责把其中已经明确的架构约束整理成 prose，避免后续实现时再次走偏。

## 0. 当前状态

- 当前唯一权威控制流文档是 [v0_pseudo.cpp](./v0_pseudo.cpp)。
- 本文档只解释已经在伪代码里落定的模块边界、生命周期和时序。
- `v1*` 文档已经废弃，不再作为实现依据。

## 1. 顶层结论

本版架构的核心结论只有三条：

1. 搜索 worker 自己参与 batch 构建，而不是把 request 丢给一套隔离 runtime 后抽身离开。
2. GPU 侧的独立控制流只负责 batch 生命周期，不负责集中承接 preprocess / postprocess。
3. 搜索与 GPU 的耦合点不是“request 入队”，而是“某个 open batch 的某一行被 claim 并填入数据”。

因此：

- `pre_process()` 在搜索线程上执行。
- `post_process()` 在 batch 完成后进入高优先级搜索 tail，由任意搜索线程执行。
- infer worker 只是一个 batch driver，用来把 batch 从 open 状态推进到 H2D / infer / D2H / completion。

## 2. 搜索侧共享状态

搜索侧当前明确维护以下共享状态：

- `search_nn_target_num`
- `search_nn_current_num`
- `head_launch_paused`
- `tailq`
- `search_work_ready`

它们的职责已经冻结为：

- `search_nn_target_num`：当前这一轮允许累计发出的 NN 请求目标数。
- `search_nn_current_num`：当前已经累计发出的 NN 请求数。
- `head_launch_paused`：当 `current >= target` 时关闭新的 `playout_head(root)` 启动。
- `tailq`：保存已经完成 NN、等待执行 `post_process()` 和剩余树更新的高优先级 tail。
- `search_work_ready`：搜索侧共享唤醒信号。高优先级 tail 入队或 root gate 重新打开时，都用它唤醒搜索 worker。

伪代码里没有把原子性和内存序逐一写出，但这里默认这些共享状态都需要正确的并发保护。

## 3. GPU 时间线模型

GPU 侧当前已经拆成 4 个语义不同的动作：

- `get_recent_slot(gpu_timeline)`
- `reserve_gpu_timeline()`
- `update_gpu_estimate()`
- `reconcile_gpu_timeline()`

它们的职责分别是：

- `get_recent_slot(gpu_timeline)`：在新 batch 第一次 claim row 时，根据当前预测时间线挑一个最快可用 slot。
- `reserve_gpu_timeline()`：当 batch 被 seal、其大小已经固定时，用当前 estimate 把这份 workload 预先登记进 timeline。
- `update_gpu_estimate()`：在一次 infer 完成后，用真实结果更新单次 infer 所需 work 的 Gamma 衰减估计。
- `reconcile_gpu_timeline()`：在 estimate 更新后，用新 estimate 回写并校正时间线。

搜索侧目标更新发生在：

- `update_gpu_estimate()`
- `reconcile_gpu_timeline()`
- `update_search_nn_target_num()`

这个顺序之后，避免搜索侧基于旧 estimate 计算新目标。

## 4. `InferHandle` 的角色

`InferHandle` 不是 request 句柄，而是一个可复用的 batch 槽位。

当前权威伪代码里，它的关键状态分成 4 类：

- open-claim 热字段：
  - `open_state = {generation, claimed_rows, sealed}`
- 发布/预约字段：
  - `slot_ready_generation`
  - `timeline_reserved_generation`
  - `bound_slot`
  - `bound_max_rows`
- batch 数据面字段：
  - `host_mem`
  - `ready`
  - `batch_done`
- inflight / GC 字段：
  - `stage`
  - `pumped_rows`
  - `final_rows`
  - `remaining_consumers`

它的语义分成 3 个阶段：

### 4.1 Open Claim 阶段

- `open_state.sealed == false`
- `open_state.claimed_rows` 表示当前代已经 claim 的 row 数
- 搜索线程可继续用 CAS claim 新 row
- 第一位 claimer 负责绑定 `bound_slot` / `bound_max_rows` 并激活 infer worker

### 4.2 Sealed / Inflight 阶段

- `open_state.sealed == true`
- batch 大小已经固定，不再接受新 row
- infer worker 负责推进 H2D / infer / D2H 状态机

### 4.3 Completion / GC 阶段

- D2H 完成后，infer worker 先固定 `remaining_consumers = final_rows`
- 然后 `batch_done.notify_all(generation)`，把这一代的所有等待 frame 发布到 `tailq`
- 每个 tail 在 `post_process()` 后做一次 `remaining_consumers--`
- 自减到 `0` 的最后一个 tail 负责切到下一代 `generation`，重新打开 handle

也就是说，一个 handle 只有在最后一个消费者离开之后才重新可用。

## 5. Open Batch Claim

当前最关键的热路径不再是“全局 `cur_hid_lock` 临界区”，
而是“每个搜索线程带一个 `hid_hint`，对每个 handle 的 `open_state` 做 CAS”。

claim 路径的当前语义是：

1. 从本 worker 的 `hid_hint` 开始扫描 ring。
2. 读取候选 handle 的 `open_state = {generation, claimed_rows, sealed}`。
3. 若 `sealed == true`，跳过这个 handle。
4. 若 `claimed_rows == 0`，尝试做 first-row CAS：
   - 把 `claimed_rows` 从 `0` 改到 `1`
   - 成功后由首个 claimer 负责：
     - 绑定 `bound_slot`
     - 计算并发布 `bound_max_rows`
     - 清空 ready flags
     - 首次激活 infer worker
5. 若 `claimed_rows > 0`，则在 `slot_ready_generation` 已发布后继续做后续 row 的 CAS claim。
6. 若 claim 后刚好达到 `bound_max_rows`，则：
   - `sealed = true`
   - `reserve_gpu_timeline_once(...)`

这些步骤仍然必须视为一个整体，因为搜索侧观察到“batch 还可写”这件事，
必须和自己成功 claim 到 row 这件事保持原子一致。

## 6. 搜索 Worker 时间线

按当前伪代码，搜索侧不再理解成“会自续接地排下一个 playout 任务”，
而是理解成“每个搜索线程一个长期驻留的 search worker”。

这个 search worker 永远按以下优先级取活：

1. 先从全局 `tailq` 取已经完成 NN、等待收尾的 `playout_tail`
2. 若没有 tail，且 `head_launch_paused == false`，则 fallback 启动一次新的 `playout_head(root)`
3. 若两者都没有，则在 `search_work_ready` 上等待

其中，一次 playout 被拆成两段：

1. `playout_head`
   - 从根部推进到 leaf
   - 若命中 NN，则负责 claim row、`pre_process()`，并把当前 frame 挂到 `batch_done`
   - 然后立即结束，不在当前线程等待 batch completion
2. `playout_tail`
   - 只在 batch completion 之后才进入 `tailq`
   - 可以由任意搜索线程执行，不要求回到原线程
   - 负责 `post_process()`、`finish_after_nn()`、以及 batch consumer GC

这里要特别说明：

- `PlayoutStateMachine` 代表的是显式 CPU 状态机，不是深层协程调用栈
- `SearchPlayoutFrame` 会跨线程流转，因此它的回收必须按 owner-worker 模型处理：
  foreign-thread release 先进入 owner worker 的 remote-free 队列，再由 owner worker 本地回收

## 7. NN Boundary 与 Tail Publication

当前伪代码里，命中 NN boundary 后的搜索侧时间线是：

1. 搜索 worker 在本地执行 `claim_and_preprocess_row_fast(...)`
2. 把 `nn_output`、`head_cpu_ticks`、wait 节点等信息写回当前 `SearchPlayoutFrame`
3. 把 frame 状态改成 `WaitingBatch`
4. 调用 `handle.batch_done.park_or_consume(generation, ...)`
5. 若 batch 已经完成，则 fast path 直接把 frame 状态改成 `TailReady` 并入 `tailq`
6. 若 batch 尚未完成，则 frame 挂进 `batch_done.waiters`
7. 未来由 infer worker 在 `notify_all(generation)` 中：
   - 把这些 frame 批量转成 `TailReady`
   - 发布到 `tailq`
   - 对每个已发布 tail 触发搜索侧唤醒

因此，当前搜索 worker 不会在 NN 路径里阻塞等待 batch completion。

## 8. Infer Worker 时间线

当前权威模型里，GPU 侧不再写成旧式的 `infer_coro()`，而是一个长期驻留的 infer worker loop。

它的主循环当前语义是：

1. 从共享 `activeq` 批量抓取新激活的 handle 到本地队列
2. 若本地队列为空，则在 infer worker 的 `work_ready` 上等待
3. 对每个 active handle 执行一次 `progress_active_handle(...)`
4. `progress_active_handle(...)` 内部按状态推进：
   - `PumpOpen`
     - 若 slot 当前 idle 且 batch 还没 sealed，则 seal 并预约 timeline
     - 若出现新的 ready row 区间，则追加 H2D
     - 当 batch 已 sealed 且所有 row 都已泵完 H2D 时，切到 `WaitLastH2D`
   - `WaitLastH2D`
     - 等最后一个 H2D 完成后发起 infer
   - `WaitInfer`
     - infer 一完成就立即发起 D2H
     - 然后立刻执行：
       - `update_gpu_estimate()`
       - `reconcile_gpu_timeline()`
       - `update_search_nn_target_num()`
       - `maybe_resume_head_launch()`
     - 最后切到 `WaitD2H`
   - `WaitD2H`
     - D2H 完成后固定 `remaining_consumers`
     - 调用 `batch_done.notify_all(generation)` 发布所有 tail
     - 从 active list 摘掉当前 handle

这里需要注意：

- seal 有两种来源：
  - batch 被 claim 满
  - GPU 在 pump 过程中发现 slot 已 idle，需要立即收口当前 batch
- 但无论哪种来源，同一个 generation 都只能 `reserve_gpu_timeline_once(...)` 一次

## 9. 当前已冻结的实现约束

当前已经足够明确、后续实现不应再偏离的点有：

- 搜索线程数直接由 `numSearchThreads` 决定。
- 每个搜索线程都应长期运行一个 search worker，而不是显式排一个“后继 root task”。
- 根部的 `head_launch_paused/search_work_ready` 是 gate；NN 路径里的核心等待点是 batch completion。
- preprocess / postprocess 不应被挪回独立 GPU 数据面线程集中执行。
- `InferHandle` 的复用必须等到最后一个消费者离开之后。
- GPU timeline 的“预约”和“结算”必须是两个不同语义的动作。
- NN completion 后的 playout tail 不要求回原搜索线程；它可以由任意搜索线程执行。
- 搜索侧调度优先级固定为：先 playout tail，后 fallback 启动新的 root playout。
- `update_search_work_stats()` 统计的是一次 playout 的总计算量：
  `playout_head` 的 CPU 时间 + `playout_tail` 的 CPU 时间，
  不把中间等待 NN completion 的时间算进去。
- 这份统计只服务于全局总计算量估计，不要求保留 head/tail 的原线程归属。

## 10. 暂不在本版展开的内容

以下内容当前明确留待后续细化，不在本版 `v0` 内冻结：

- root 切换
- 手动暂停 / 恢复搜索
- 多个 `Search` 实例共存
- 多个 evaluator 共存
- 具体的原子类型、内存序和锁粒度
- 伪代码中的 spinning helper 最终如何降本实现
