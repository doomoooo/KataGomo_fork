# 计划

本文档用于追踪 TensorRT 调度与搜索侧架构演进的整体计划。

## plan_v0

状态：当前生效的修订版

### 0. 2026-03-23 架构澄清

此前围绕 `v0` 的实现探索已经证明，如果把搜索运行时做成“coordinator 轮询 + permit queue + per-playout task”的形态，会和这里真正想要的长期架构发生实质偏离。

本次修订明确冻结以下事实：

- 搜索侧的基本执行单元是 `playout coroutine`，不是 “session task” 或 “permit task”。
- 搜索协程只有一个 yield 点：一次 playout 产出 NN 提交之后，等待 GPU 结果的那个点。
- 一次 playout 若未产出 NN 提交，则整个 playout 结束前都不可打断；是否继续，只能在 playout 边界判断。
- GPU 侧在一次 infer 完成后，需要先更新自己的时间估计，再反推“到下一个估计完成点为止，搜索侧应维持多少个 NN 任务目标数量”，然后再唤醒等待中的搜索协程。

后续实现必须以这组约束为准；与之冲突的中间方案不再继续演进。

### 1. 背景

当前 TensorRT 路径已经完成 I/O overlap，但单个调度线程仍然承担了过多工作。在已有 benchmark 中：

- `scheduler_busy_time_share` 很高。
- `infer_stream_occupancy` 明显低于理想的接近打满状态。
- 调度线程不仅负责调度决策，还负责 TensorRT 专属的 row 级预处理、H2D 提交、输出后处理和结果发布。

这在高 QPS、多 GPU 场景下已经成为一个真实的可扩展性问题。

与此同时，搜索侧还存在另一类结构性低效：

- 一次 playout 的终点并不总是一次 NN request。
- 相当一部分 playout 会因为 edge-visit 冲突而提前终止，然后回到根节点重新开始。
- 因此，即使 GPU 立刻需要更多 NN request，一部分 CPU 线程也可能在长尾时间内不断碰壁，迟迟产不出 request。

这意味着，当前“一条搜索线程持续执行一个搜索 worker”的模型，在搜索线程数量被精确压低到“刚好喂饱 GPU”的附近时，可能同时让 CPU 和 GPU 都处于等待状态。

### 2. 核心问题定义

这里实际上有两个相互耦合的问题：

1. 当前 TensorRT scheduler 将过多数据面工作集中在单线程上。
2. 当前搜索执行模型以固定线程在 playout 粒度上生产 NN request，导致 request 生产存在明显长尾。

这两个问题会互相放大：

- 如果只优化 TensorRT scheduler，搜索侧仍可能喂不满 GPU。
- 如果只优化搜索侧，TensorRT scheduler 仍可能继续成为 CPU 瓶颈。

因此，长期方案必须以端到端视角统一规划，而不是孤立地做局部优化。

### 3. 总体目标

目标是构建一套面向 TensorRT 的推理调度架构，使其能够：

- 在高 QPS、多 GPU 场景下最大化端到端吞吐。
- 在正确的时间给 infer stream 提供数量恰当的 request。
- 在收益足够时尽量减少不必要的 host 侧拷贝。
- 能够自然演进到基于协程、而非固定搜索线程的更细粒度 playout 调度架构。

### 4. 非目标

以下内容明确不属于这条计划线当前要维护的目标：

- 不要求非 TensorRT 后端也跟随同样的设计。
- 不为了抽象层级整洁而牺牲可测量性能。
- 不在边界和约束尚未厘清之前，过早锁死最终实现细节。

如果追求峰值性能需要 TensorRT 拥有一条 backend-specific fast path，以及 backend-specific 的内部契约，这是允许的。

### 5. 硬约束

- 优先级是最高性能，而不是抽象纯洁性。
- 允许 TensorRT 专属代码打破现有抽象层级，但边界必须清晰。
- 即使存在 fast path，其所有权、同步方式和生命周期也必须明确、可维护。
- 允许对搜索侧进行大规模架构改动，但必须有清晰规划。
- 整个工作过程需要通过逐步细化的计划版本来追踪。

### 6. 长期架构方向

长期方向是：

- 将工作调度从当前固定搜索线程模型中解耦出来。
- 以 playout 尝试和 NN request 需求为核心粒度来思考调度。
- 最终使用协程管理 playout，而不是让一个 coordinator 去调度大量短生命周期 task。

在这个模型下：

- 搜索侧存在一个共享区域，统一维护：
  - 全局累计的 NN 提交计数。
  - 全局累计的 NN 完成计数。
  - 当前窗口发布的 NN 提交绝对目标计数。
  - 全局启停信号。
  - 近期单次 playout 平均 CPU 时间。
  - 近期单次 playout 成功产出 NN 提交的概率。
- 这些近期统计量采用 gamma 衰减的加权均值表示，并且必须能 `O(1)` 维护。
- CPU 侧不再由中心循环高频轮询决定是否继续，而是在每次 playout 边界根据共享区状态做一次本地决策。
- GPU 侧根据各 infer stream 的时间估计，反推下一时间段所需的 NN 任务目标数量。
- 调度目标不是简单“越多越好”，而是让搜索侧在正确的时间维持正确数量的 in-flight NN 任务。

### 7. 面向需求的搜索模型概念

未来搜索侧架构预期大致如下：

- 工作粒度从线程转向 `playout coroutine`。
- 一次 playout 尝试可能在没有产出 NN request 的情况下结束。
- 搜索协程的控制规则必须严格如下：
  1. 如果一次 playout 结束但没有生成 NN 提交：
     - 更新共享区里的近期统计量。
     - 检查全局启停信号。
     - 若继续，则直接开始下一次 playout；若停止，则协程结束。
  2. 如果一次 playout 结束并生成了 NN 提交：
     - 先更新共享区里的近期统计量。
     - 再递增全局 NN 提交计数。
     - 若这次递增使其达到或超过当前窗口发布的绝对目标计数，则关闭本轮 generation gate。
     - 若未达到，则允许新的协程启动下一次 playout。
     - 当前协程在此处 yield，等待本次 GPU 任务完成后恢复，并继续更新搜索树；其局部状态必须保留。
- 除上述 GPU 等待点外，搜索协程没有第二个 yield 点。
- GPU 侧在一次 infer 完成后，处理顺序必须是：
  1. 更新 GPU 侧近期时间估计。
  2. 结合新的 GPU 时间估计、搜索侧单次 playout 平均时间、单次 playout 成功概率，计算直到下一次估计完成点为止应维持的 NN in-flight 数量。
  3. 基于当前全局 NN 完成计数，将它转换成当前窗口发布的 NN 提交绝对目标计数。
  4. 再唤醒所有等待中的搜索协程。
- 这里的“目标”在共享区里不应表示成局部 `outstanding` target，而应表示成全局累计计数上的绝对水位线。
- 因为搜索协程在 playout 内不可打断，达到目标后允许存在少量额外 NN 提交；这些额外提交不需要回滚，而应作为下一次 GPU 重估时必须吸收的真实状态。
- 目标数量本质上是一个“截至下一时间窗口所需的 request debt”估计，而不是简单的 ready queue 上下水位。

这里描述的是概念目标，而不是当前已经敲定的 API 设计。

### 8. 当前阶段的规划需求

在协程化搜索运行时尚不存在之前，TensorRT 调度重构必须考虑它将来如何与协程架构衔接。

具体来说：

- 基于线程的 TensorRT 重构方案，与基于协程的 TensorRT 重构方案，代码形态可能差异很大。
- 零拷贝或少拷贝优化很容易穿透大量现有抽象层级。
- 在当前线程模型下看起来合理的局部优化，未来可能会与协程模型强烈冲突。

因此，当前阶段不能只看短期 benchmark 增益，还必须评估它是否建立了足够干净、足够前向兼容的边界。

### 9. 工作流拆分

#### 工作流 A：TensorRT 调度与数据面重构

关注点：

- 降低或移除单调度线程瓶颈。
- 明确 TensorRT 专属预处理和后处理的归属位置。
- 在收益明确时减少额外拷贝。
- 明确 row/batch buffer 的所有权和生命周期。

需要回答的问题：

- 哪些工作必须在 infer stream 或 context 粒度上串行化？
- 哪些工作可以安全地下沉到 request 生产路径？
- 为了去掉一次 host-side copy，可以接受多高的状态机复杂度？
- TensorRT-only fast path 可以接受怎样的内部契约？

#### 工作流 B：搜索侧 playout 生产模型

关注点：

- 明确共享区里所有运行时状态的精确定义。
- 度量 playout 尝试数与 NN request 产出数之间的差距。
- 度量 edge-visit 冲突带来的 request 生产长尾。
- 定义“单次 playout 结束后是否继续”的局部决策规则。

需要回答的问题：

- 全局累计 NNEval count 与当前窗口绝对目标计数如何在共享区中表示？
- gamma 衰减系数如何选择，才能同时兼顾稳定性与响应速度？
- playout 边界上需要原子更新哪些量，才能让决策保持 `O(1)`？
- “停止”应该表示为全局 gate、epoch，还是其它更稳健的形式？

#### 工作流 C：协程化运行时

关注点：

- 将当前以线程为中心的搜索执行模型改造成以协程为中心的 playout 调度模型。
- 保证搜索协程只有一个 yield 点。
- 让 GPU infer 完成成为搜索侧下一轮唤醒与目标重估的主时钟。
- 在提高吞吐的同时保持搜索正确性和搜索质量。

需要回答的问题：

- 一个 in-flight playout coroutine 的局部状态应由什么抽象表示？
- 树锁、virtual loss、NN wait 等语义在“单 yield 点”约束下如何表达？
- 搜索协程的创建、挂起、恢复分别由谁负责？
- GPU 完成回调与搜索协程恢复之间的所有权和调度顺序如何保证？

### 10. 建议阶段划分

#### Phase 0：规划与边界定义

交付物：

- 对问题与目标方向的精确定义。
- TensorRT fast path 的 backend-specific 边界定义。
- 未决设计问题与验证指标列表。

本文件是 Phase 0 的第一份产出。

#### Phase 1：TensorRT fast path 重构

交付物：

- 一套明确的 TensorRT-only 调度设计。
- 对 buffer、request、row/batch 生命周期的清晰定义。
- 一套能够验证 scheduler CPU 瓶颈是否下降的验证方案。

这一阶段仍然可以暂时使用 OS 线程，只要它不会阻碍后续协程化演进。

#### Phase 2：搜索侧需求模型

交付物：

- playout 到 request 的转化率指标。
- 单次 playout 平均时间与成功概率的 gamma 衰减模型。
- 目标 NN 任务数量的计算规则。
- 一套在 playout 边界执行、且为 `O(1)` 的继续/停止控制规则。

#### Phase 3：协程化 playout 运行时

交付物：

- 协程管理的搜索执行模型。
- “单 yield 点” 的 playout coroutine 协议。
- 基于 GPU 需求预测的动态 playout 生产机制。
- GPU infer 完成后先重估目标、再统一唤醒搜索协程的整合方案。

### 11. 关键设计原则

- 先对可测量吞吐负责，再谈抽象美观。
- backend-specific 的复杂度应尽量局部化，而不是强行塞进通用抽象。
- 不能接受隐式的所有权或同步规则；只要存在 fast path，它的契约就必须被明确写下来。
- 优先采用分阶段迁移，但不能为了短期过渡方案锁死一个会与长期协程模型冲突的结构。
- 搜索侧不能退化成高频中心轮询器；决策必须尽量下沉到 playout 边界。
- 搜索协程必须只有一个 yield 点；任何额外 yield 都需要被视为架构偏离。
- GPU 侧必须拥有“先更新估计、再计算目标、后唤醒搜索协程”的明确时序。

### 12. plan_v1 需要进一步回答的问题

下一版计划需要更具体地回答以下问题：

- TensorRT 数据搬运与 TensorRT 数据原地变换之间的边界应如何严格定义？
- 如果消除一次 host-side copy 会显著提高状态机复杂度，这个代价是否值得？
- 什么样的 TensorRT 中间重构方案，最有利于后续衔接协程化 playout 调度？
- 需求驱动的 playout 生产，需要哪些精确的共享区统计量？
- 目标 NN 任务数量应如何被 GPU 侧时间模型重新估计？
- 搜索协程的唯一 yield 点，应该落在什么 sender / awaitable 协议上？
- 从当前线程模型迁移到这种“单 yield 点 + GPU 反推目标”的协程运行时，最小可行路径是什么？
