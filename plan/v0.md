### 2. 核心架构结论

本版冻结的核心结论只有一条：

- 搜索协程不是把 request 丢给一套完全隔离的 GPU runtime 然后抽身离开。
- 搜索协程自己负责：
  - 选择并占用一个 open batch 的 row
  - 对该 row 做预处理
  - 等待该 batch 完成
  - 在恢复后做后处理

也就是说：

- `preprocess / postprocess` 被主动分散到搜索线程上
- GPU 侧只保留一条轻量的 infer 控制流，负责：
  - open batch 的 launch
  - H2D / infer / D2H
  - GPU 时间估计更新
  - recent slot 更新
  - 搜索侧目标数量更新
  - batch 完成通知

这和之前“GPU 侧单独再造 `PackExecutor / PostExecutor` 数据面”的理解不同。

### 3. 搜索侧的基本执行模型

本版下，搜索侧的基本单元仍然是 `playout coroutine`。

但它的职责现在更具体：

- 做完整的搜索侧 CPU 相位
- 在需要 NN 时，自己进入一次 GPU 协作流程
- GPU 完成后，仍回到同一搜索协程继续完成本次 playout 的后半段

从控制流上看，一次带 NN 的 playout 大致是：

1. 搜索协程完成当前 leaf / edge 的搜索侧收尾。
2. 选择一个 open batch，并在该 batch 中占用一个 row。
3. 搜索协程自己对该 row 做预处理，直接写入该 batch 对应的 pinned host 内存。
4. 搜索协程等待该 batch 的完成事件。
5. batch 完成后，搜索协程恢复，在同一搜索线程上做本 row 的后处理。
6. 搜索协程继续回填搜索树，并在回到根部后决定是否继续下一次 playout。

这意味着：

- “等 GPU”这一点仍然是搜索协程的中心挂起点。
- 搜索侧不会把 preprocess / postprocess 再集中回一个单独的 GPU 调度线程。

### 4. 推理侧不是完整 runtime，而是 batch 控制流

本版不再把 infer 侧理解成一套独立的“大 runtime”。

更准确地说，它只是一个专门处理 batch 生命周期的控制流。

`v0_pseudo.py` 当前表达的 infer 侧职责包括：

- 维护一组可循环复用的 `InferHandle`
- 为新 batch 选择 slot
- 观察 row 是否 ready
- 发起 H2D
- 发起 infer launch
- 发起 D2H
- 在 launch / finish 时更新 GPU 可用性估计
- 在合适的完成点更新搜索侧目标数量
- 批量唤醒等待中的搜索协程

所以本版对 infer 侧的理解是：

- 它是 batch 生命周期控制者
- 不是搜索侧数据面的拥有者

### 5. 共享状态

按 `v0_pseudo.py`，当前至少存在三类共享状态。

#### 5.1 搜索侧共享状态

搜索侧显式维护：

- `search_nn_target_num`
- `search_nn_current_num`
- `search_coro_pause`
- `search_coro_notice`

本版只冻结它们的“职责方向”，暂不冻结最终字段名和精确算式：

- 搜索侧需要知道当前目标 NN 数量
- 搜索侧需要知道当前已占用的 NN 数量
- 搜索侧需要有一个“暂停继续生成”的 gate
- 搜索侧需要有一个“暂停转继续”的通知原语

它们的精确数学含义、是否最终要改写成别的累计计数形式，留给后续版本继续收敛。

#### 5.2 GPU 选择共享状态

推理侧显式维护：

- `recent_slot`
- `recent_slot_lock`

它表达的是：

- 当前根据 GPU 运行状态估计出的“最值得放下一批”的 slot

这个状态会在：

- infer launch
- infer finish

等时刻更新。

#### 5.3 open batch 池

推理侧还维护：

- `infer_handles`
- `cur_hid`

这里的 `InferHandle` 本质上是：

- 一个 pinned host batch buffer
- 一个当前 row 计数器
- 一组 row-ready 标记
- 一个 batch 完成通知对象
- 一个保护 open batch 生命周期的锁

### 6. `InferHandle` 的角色

本版明确把 `InferHandle` 视为“open batch / in-flight batch 的载体”。

它至少承载以下语义：

- 这个 batch 最终跑在哪个 `Slot`
- 当前已经分配了多少 row
- 哪些 row 已经完成预处理，可以被 infer 控制流消费
- 这个 batch 何时整体完成

因此，`InferHandle` 不是“单 request 句柄”，而是“batch 句柄”。

这也是当前架构区别于传统 request queue 的关键点：

- 搜索协程并不是把一个 request 发到队列里就结束
- 它会先参与把自己的 row 填进某个 batch，再等待该 batch 完成

### 7. open batch 的关键临界区

`v0_pseudo.py` 里最关键、也最复杂的一段就是 open batch 临界区。

本版明确冻结这一点：

- “检查当前 handle 是否还能接 row”
- “如果这是新 batch，则为它选 slot”
- “读取当前 row 编号”
- “递增 row 计数器”

这四步必须被视为一个临界区。

原因很简单：

- 如果搜索协程刚选定某个 open batch
- 而 infer 控制流已经根据旧状态把这个 batch 提前 launch
- 那么搜索协程手上的 row 选择就失效了

所以 open batch 的生命周期不是一句“找个有空位的 batch”就能说清的，它必须被显式建模成：

- row 分配
- batch 封顶
- launch ownership

之间的受保护状态迁移。

### 8. 搜索协程时间线

按 `v0_pseudo.py`，搜索协程的完整时间线应理解为：

1. 在树上完成本次 playout 的 CPU 相位。
2. 如果当前 leaf 需要 NN：
   - 提升目标数量
   - 必要时关闭搜索继续生成
   - 预先补上一条后继 playout，保持任务数量稳定
   - 进入 GPU 协作流程
3. GPU 协作流程里：
   - 找到一个可用的 `InferHandle`
   - 为自己占用一个 row
   - 在本搜索线程上做 `pre_process`
   - 标记该 row 已 ready
   - 等待整个 batch 完成
   - 恢复后做 `post_process`
4. 之后搜索协程继续 `update(node)`，再一路回到根部。
5. 回到根部后：
   - 更新搜索侧统计
   - 依据 pause / notice 决定是否继续
   - 若这次没有产出 NN，则补上一条后继 playout

这条时间线说明：

- 搜索协程既负责搜索，也直接参与 batch 构建
- search / infer 的边界不是“request 入队”
- 而是“row 被占用并写入 pinned host buffer”

### 9. infer 控制流时间线

按 `v0_pseudo.py`，infer 控制流的大致时间线是：

1. 观察某个 `InferHandle` 当前已经分配了多少 row。
2. 等待这些 row 的 `ready` 标记就绪。
3. 对连续 ready 的 row 段发起 H2D。
4. 若当前 GPU 处于 idle，则强制把这个 batch 封顶并尽快 launch。
5. 等最后一段 H2D 完成后，发起 infer。
6. infer 结束后，发起 D2H。
7. 在 launch / finish 等关键点更新 GPU 估计、GPU idle 状态和 recent slot。
8. 在合适的完成点更新搜索侧目标数量。
9. 通过 batch 级通知唤醒所有等待该 `InferHandle` 的搜索协程。

所以 infer 控制流的核心职责是：

- 不断把 open batch 推过 H2D / infer / D2H 三个阶段
- 并在 GPU 状态变化时及时更新“下一批该落在哪个 slot”

### 10. 为什么这一版比旧理解更接近真实目标

这版方向和之前最本质的不同是：

- 之前更像“搜索协程把请求交给 GPU runtime”
- 现在更像“搜索协程直接参与 batch 组装，然后等待 batch 级完成”

这样做的好处是：

- `preprocess / postprocess` 压力被天然分散到搜索线程
- infer 控制流只保留真正需要集中维护的 GPU 生命周期逻辑
- 搜索协程能自然要求“恢复时仍回到同一搜索线程”

因此，本版的重点不再是继续设计一套抽象上更完整的 GPU runtime，而是先把：

- open batch 的所有权
- row 分配临界区
- batch 完成通知

这三件事讲清楚。

### 11. 当前明确省略的内容

按你的说明，本版 `v0` 明确不展开以下内容：

- 搜索侧和推理侧时间估计的精确数学细节

- 手动暂停 / 恢复搜索
- 多个 `Search` 实例共存
- 多个 `NNEvaluator` 实例共存，例如 humanSL
- 最终实现时 `infer_coro` 的高效落地方式

这些都留给下一版伪代码和后续文档。

### 12. 接下来 `v1 / v2` 必须回答的问题

基于当前 `v0_pseudo.py`，后续文档必须继续细化：

- `search_nn_target_num / search_nn_current_num` 的最终精确定义是什么
- search pause / notice 是否应被视为独立挂起点，还是纳入同一等待机制
- `InferHandle` 的完整生命周期、重置和复用规则是什么
- batch 完成后由谁负责做“第一个唤醒协程”的额外工作
- `recent_slot` 的估计模型和更新时机如何定义
- 异构多卡下，不同 GPU 的 batch / stream 配置如何映射进这套控制流

### 13. 当前版本的结论

本版 `v0` 最终只冻结以下结论：

1. 当前主架构应以 [v0_pseudo.py](./v0_pseudo.py) 为准。
2. 搜索协程直接参与 open batch 的 row 分配、预处理、等待和后处理。
3. infer 侧只保留 batch 生命周期控制，而不是再拥有完整的数据面。
4. open batch 的 row 分配与 launch 之间必须存在明确临界区。
5. 真正需要优先细化的，不是再发明新抽象，而是把 `InferHandle` / open batch / completion 的生命周期写严密。
