# 计划

本文档冻结当前生效的总架构方向。

控制流以 [v0_pseudo.py](./v0_pseudo.py) 为准；本文只负责把其中已经明确的架构约束整理成 prose，避免后续实现时再次走偏。

## 0. 当前状态

- 当前唯一权威控制流文档是 [v0_pseudo.py](./v0_pseudo.py)。
- 本文档只解释已经在伪代码里落定的模块边界、生命周期和时序。
- `v1*` 文档已经废弃，不再作为实现依据。

## 1. 顶层结论

本版架构的核心结论只有三条：

1. 搜索协程自己参与 batch 构建，而不是把 request 丢给一套隔离 runtime 后抽身离开。
2. GPU 侧的独立控制流只负责 batch 生命周期，不负责集中承接 preprocess / postprocess。
3. 搜索与 GPU 的耦合点不是“request 入队”，而是“某个 open batch 的某一行被 claim 并填入数据”。

因此：

- `pre_process()` 在搜索线程上执行。
- `post_process()` 在等待 batch 完成后，仍回到原搜索协程上执行。
- `infer_coro()` 只是一个 batch driver，用来把 batch 从 open 状态推进到 H2D / infer / D2H / completion。

## 2. 搜索侧共享状态

搜索侧当前明确维护 4 个共享变量：

- `search_nn_target_num`
- `search_nn_current_num`
- `search_coro_pause`
- `search_coro_notice`

它们的职责已经冻结为：

- `search_nn_target_num`：当前这一轮允许累计发出的 NN 请求目标数。
- `search_nn_current_num`：当前已经累计发出的 NN 请求数。
- `search_coro_pause`：当 `current >= target` 时关闭新的搜索继续生成。
- `search_coro_notice`：GPU 侧更新目标后，用来唤醒暂停在根部的搜索协程。

伪代码里没有把原子性和内存序逐一写出，但这里默认这些共享状态都需要正确的并发保护。

## 3. GPU 时间线模型

GPU 侧当前已经拆成 4 个语义不同的动作：

- `get_recent_slot(gpu_timeline)`
- `reserve_gpu_timeline()`
- `update_gpu_estimate()`
- `reconcile_gpu_timeline()`

它们的职责分别是：

- `get_recent_slot(gpu_timeline)`：在新 batch 第一次 claim row 时，根据当前预测时间线挑一个最快可用 slot。
- `reserve_gpu_timeline()`：当 batch 被 seal、其大小已经固定时，用当前 estimate 把这份 workload 预先登记进 timeline。
- `update_gpu_estimate()`：在一次 infer 完成后，用真实结果更新单次 infer 所需 work 的 Gamma 衰减估计。
- `reconcile_gpu_timeline()`：在 estimate 更新后，用新 estimate 回写并校正时间线。

搜索侧目标更新发生在：

- `update_gpu_estimate()`
- `reconcile_gpu_timeline()`
- `update_search_nn_target_num()`

这个顺序之后，避免搜索侧基于旧 estimate 计算新目标。

## 4. `InferHandle` 的角色

`InferHandle` 不是 request 句柄，而是 batch 句柄。

它当前至少承载以下状态：

- `cur_row`
- `ready`
- `seal`
- `slot`
- `host_mem`
- `complete`
- `lock`

它的语义分成 3 个阶段：

### 4.1 Open 阶段

- `seal == False`
- `cur_row` 表示“下一可分配 row 编号”
- 新的搜索协程可以继续 claim row

### 4.2 Sealed / Inflight 阶段

- `seal == True`
- batch 大小已固定
- `infer_coro()` 只消费已经 claim 的 row，不再接受新 row

### 4.3 Completion / GC 阶段

- `handle.complete.notify_all()` 之后，所有等待该 batch 的搜索协程开始恢复
- 此后 `cur_row` 不再表示“已分配 row 数”，而转为“剩余待回收消费者数”
- 每个恢复后的搜索协程在 `post_process()` 之后对它做一次递减
- 自减到 `0` 的最后一个协程负责：
  - `ready.fill(False)`
  - `seal = False`
  - `complete.reset()`

也就是说，一个 handle 只有在最后一个消费者离开之后才重新可用。

## 5. open batch 临界区

当前最关键的临界区在 `playout_gpu()` 里。

它必须原子地完成以下动作：

1. 选择当前 `cur_hid` 指向的 handle。
2. 检查它是否已经 `seal`。
3. 若已 seal，则推进到下一个 handle 并重试。
4. 若这是空 batch，则用 `get_recent_slot(gpu_timeline)` 绑定 slot。
5. 读取当前 `cur_row`。
6. 递增 `cur_row`，claim 本协程使用的 row。
7. 若 claim 后刚好达到 `max_batch`，则：
   - `reserve_gpu_timeline()`
   - `seal = True`

这几步必须视为一个整体，因为：

- 如果搜索协程先观察到“这个 batch 还可写”
- 但 infer 侧已经把它 seal 并准备 launch
- 那么搜索协程手里的 row 选择就会失效

## 6. 搜索协程时间线

按当前伪代码，一次搜索协程的大致流程是：

1. 若在根部并且 `search_coro_pause == True`，先等待 `search_coro_notice`。
2. 做一次 playout 的搜索侧推进。
3. 若继续下探子节点，则逻辑上递归进入子节点 playout。
4. 若当前 leaf 需要 NN：
   - `search_nn_current_num += 1`
   - 若 `current >= target`，则置 `search_coro_pause = True`
   - 先补发一个新的 `playout(root)`，保证线程上始终有下一个 playout 排队
   - 进入 `playout_gpu(data)`
5. `await playout_gpu(data)` 返回后，继续本次 playout 的树更新。
6. 若递归回到根部且本次没有产出 NN，则补发下一次 `playout(root)`。

这里要特别说明一件事：

- `await playout(child)` 在伪代码里表达的是“逻辑递归的 playout 推进”
- 最终 C++ 实现不应真的保留深层协程调用栈，而应改写成显式状态机或等价的迭代结构

## 7. `playout_gpu()` 时间线

`playout_gpu()` 的职责是让搜索协程自己完成 batch claim、预处理、等待和回收：

1. 进入 open batch 临界区，找到一个未 seal 的 `InferHandle`。
2. 若这是空 batch，则调用 `get_recent_slot(gpu_timeline)` 绑定 slot。
3. claim 一个 row。
4. 若 claim 之后 batch 已满，则立即：
   - `reserve_gpu_timeline()`
   - `seal = True`
5. 若这是第一个 row，则启动 `infer_coro(handle)`。
6. 搜索协程自己执行 `pre_process()`。
7. 把 `ready[row] = True`。
8. `await handle.complete`。
9. 恢复后执行 `post_process()`。
10. 进入 GC 阶段，对 `cur_row` 自减。
11. 若自己是最后一个离开的协程，则负责把 handle 重新打开。

## 8. `infer_coro()` 时间线

`infer_coro()` 是一个 spinning thread 风格的 batch driver。

它的主循环当前语义是：

1. `await sleep(0)`，让调度器有机会切换。
2. 读取当前 `row` 和 `seal` 状态。
3. 若 GPU 当前 idle，且这个 batch 还没 seal，则：
   - `reserve_gpu_timeline()`
   - `seal = True`
4. 若存在新的 row 区间 `[row_low, row)`，则：
   - 等待这些 row 的 `ready`
   - 对这段 row 发起 H2D
   - 推进 `row_low`
5. 若 batch 已 seal，则退出主循环。
6. 等最后一个 H2D 完成。
7. 发起 infer。
8. 发起 D2H。
9. 在 completion 点执行：
   - `update_gpu_estimate()`
   - `reconcile_gpu_timeline()`
   - `update_search_nn_target_num()`
10. `notify_all()` 唤醒等待该 batch 的所有搜索协程。

这里需要注意：

- seal 有两种来源：
  - batch 被 claim 满
  - GPU 在 spin 过程中变 idle，需要立即收口当前 batch
- 但无论哪种来源，同一个 batch 都只能 `reserve_gpu_timeline()` 一次

## 9. 当前已冻结的实现约束

当前已经足够明确、后续实现不应再偏离的点有：

- 搜索线程数直接由 `numSearchThreads` 决定。
- 每个搜索线程都应长期维持“恰好一个下一次 playout 在排队”的稳态。
- 根部的 `search_coro_pause/search_coro_notice` 是 gate；NN 路径里的核心等待点是 batch completion。
- preprocess / postprocess 不应被挪回独立 GPU 数据面线程集中执行。
- `InferHandle` 的复用必须等到最后一个消费者离开之后。
- GPU timeline 的“预约”和“结算”必须是两个不同语义的动作。

## 10. 暂不在本版展开的内容

以下内容当前明确留待后续细化，不在本版 `v0` 内冻结：

- root 切换
- 手动暂停 / 恢复搜索
- 多个 `Search` 实例共存
- 多个 evaluator 共存
- 具体的原子类型、内存序和锁粒度
- 伪代码中的 spinning helper 最终如何降本实现
